These are configuration/readiness findings, not evidence that all existing implementation is broken.

The inspected application is **NAVI Live Notifier**, application/client ID **REDACTED_DISCORD_ID**. General Information and OAuth2 show the same public ID. The local effective `DISCORD_CLIENT_ID` is empty, so an application-ID match is not yet established. A bot user exists; its token was neither revealed nor reset. ## Configuration instructions

1. Open the existing [NAVI application](https://discord.com/developers/applications/REDACTED_DISCORD_ID/information). Do not create another application. Confirm the public application ID above and use that ID for `DISCORD_CLIENT_ID`.
2. Open **OAuth2 → Redirects → Add Redirect**. For this Windows localhost setup, enter exactly `http://localhost:3000/api/auth/callback/discord` and save. Keep **Public Client** off. No trailing slash, alternate host or wildcard should be substituted.
3. If running in Codespaces or another HTTPS host instead, set `WEB_ORIGIN` to its actual forwarded website origin and register that exact origin plus `/api/auth/callback/discord`. A Codespaces editor URL is not the forwarded application origin. Keep the forwarded website private for personal testing, and keep the bot broker unforwarded. Production authentication requires HTTPS; HTTP localhost is for development mode. Restart the web process after changing its origin.
4. Configure service files privately from the existing examples, without overwriting populated files. Put the OAuth client secret only in `.env.web`, and the bot token only in `.env.bot`. Use existing securely saved credentials; do not reset either simply to inspect it. If a credential has been lost, rotate it yourself in the appropriate Portal page and update its service file privately. Never paste credentials into this report, chat, URLs, screenshots or public environment variables.
5. Populate the personal user allowlist, auth secret and matching broker secret. Generate the two distinct secrets locally in a trusted password manager or directly into the ignored files; keep them stable across restarts. `BOT_INTERNAL_URL` and `BOT_STATUS_PORT` must agree. Both example service files are safe templates; the real files are ignored by `.gitignore`.
6. Open **Installation** and keep **Guild Install** enabled. Disable **User Install** for this server-only workflow. For an installable public bot using **Discord Provided Link**, add `bot` under **Default Install Settings → Guild Install → Scopes** (Discord may also retain/include `applications.commands`). Select only **View Channels**, **Send Messages**, and **Embed Links**: **19456 = 1024 + 2048 + 16384**. Save changes. Do not add `identify guilds` here; the website requests those separately during login.
7. For the recommended owner-only testing setup, choose **Install Link → None** and save, then turn **Public Bot** off under **Bot** and save. Continue installing through NAVI's existing explicit guild-specific URL as the application owner. The Portal-provided default link is unnecessary in this mode; if the Portal rejects a private application with a default authorization link, remove that link first rather than enabling public installation as a workaround. Public Bot on is needed only if other users are intentionally allowed to install. This restriction is independent of the website's personal user allowlist.
8. On **Bot**, keep **Requires OAuth2 Code Grant**, **Presence Intent**, **Server Members Intent**, and **Message Content Intent** off. No Gateway connection is opened by the current runtime. The disconnected discord.js scaffold declares only the ordinary `Guilds` intent; it has no privileged Portal toggle. An offline bot indicator is therefore expected and does not prove REST requests will fail. See [Discord Gateway intents](https://docs.discord.com/developers/events/gateway).
9. Start PostgreSQL using the existing local setup, run `npm run db:check`, review all existing migrations and apply them with `npm run db:migrate` to the intended development database. Current migrations include auth, streamer registration and notification settings; older Phase 2 instructions describing only four auth tables are historical. No migration was applied during this review.
10. Run `npm run env:check:auth`, then start the existing web and bot services (for example, `npm run dev:web` and `npm run dev:bot` in separate terminals). Start login from NAVI so Better Auth creates browser-bound state; do not use a hand-built login URL or manually visit the callback. The consent request should contain only `identify guilds`.
11. Use a test guild where your account is owner or has Administrator/Manage Server. Select it in NAVI and use the existing Install action if needed. Approve only the expected bot permissions. Return to NAVI and refresh installation status; a redirect or Portal install counter alone is not authoritative.
12. In Discord, inspect the bot's actual guild role and ordinary text-channel overwrites. It must have **View Channel** and **Send Messages** for an eligible destination. The existing 19456 install mask also grants Embed Links for the approved notification contract, although the current labelled test is plain text. Do not grant Administrator, Manage Roles or Mention Everyone. Optional alert roles must be mentionable, unmanaged and not @everyone; no role mention is required for a basic test. Effective permissions depend on guild roles and channel overwrites, not the Portal calculator. See [Discord permissions](https://docs.discord.com/developers/topics/permissions).
