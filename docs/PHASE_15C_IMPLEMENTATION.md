# Phase 15C — secure PostgreSQL command processing

Date: **2026-10-22**. Implemented the opt-in queue/admission/processor foundation approved by the owner. **The existing dashboard and startup paths remain unchanged.** Phase 15D UI/transport cutover and Phase 15F cloud configuration are not implemented; focused security/reliability tests required by Phase 15C do not constitute a separate Phase 15E rollout.

## Implemented behavior

- Strict allowlists for installation refresh, target refresh, settings apply and explicit test send. Canonical validated payloads, bounded JSON, UUID keys and sanitized typed results/errors. Unknown fields, arbitrary endpoints/SQL, credentials in additional payload fields and invalid templates are rejected.
- Server-side admission adapter requires a session resolver, fresh guild-authorizer and exact same-origin submission. It derives requester identity from the authenticated user and binds the internal session row ID, not its token. Database admission independently checks session/user/Discord-account consistency, user/guild scope and settings ownership/version. The policy hash prevents executing commands admitted under a different backend policy.
- Persistent command/attempt/snapshot tables, guild-wide idempotency, actor ownership on result reads, database-clock TTL, transactional admission/test reservation, per-actor/per-guild pending caps (10/20), SKIP LOCKED claims, 60-second renewable leases, ownership generations and at most three claims.
- Explicit pending/processing/completed/failed/expired/uncertain states. Cancelled is reserved in the schema; there is no cancellation UI/API in this phase. Recovery safely reschedules unstarted work or expires it and quarantines possible sends. No automatic uncertain retry or exactly-once claim.
- Bot-side current membership/owner/Administrator/Manage Guild validation through targeted official REST endpoints, plus existing fresh bot channel/role/mention checks. Guilds remains the only Gateway intent. Existing Discord REST client, limiter and sender are shared; no second sender or bot connection was introduced.
- Settings and command acknowledgment commit in the same outer database transaction; the existing notification repository runs in its transaction/savepoint and retains its version and route-lock behavior. Immediate legacy DB-only disable remains unchanged and invalidates older queued saves.
- Test sends reload saved config, use the existing route coordinator throughout external I/O, persist an effect-start marker before calling the sender, and use the original deterministic nonce. The new receipt-capable sender method validates message/channel IDs. Legacy `sendTest`/`sendLive` responses stay unchanged.
- Receipt evidence is journaled against the original marked attempt, including a valid late receipt after lease loss; this does not overwrite uncertain state or authorize a resend. Test ledger and final command acknowledgment are committed together. Logs contain only bounded event/code/command metadata, never exception messages, credentials or SDK objects.

Factories are deliberately inert. `createCommandAdmission` installs no routes, and `createCommandProcessor` starts no polling/Gateway/worker. Its explicit `runOne` method processes at most one claimed command with an in-flight guard and lease renewal. Existing `apps/bot/src/index.ts`, website runtime and monitoring worker are not wired to it. `discordBotServices().commandAccess` merely exposes adapters around the existing REST instance; constructing it performs no command work.

## Decisions and migration

Read the A/B audit, design and verification before changes. Resolved the allowed retention/reference choices conservatively:

- Soft user/session/subscription references retain evidence after logout/removal; live validity is checked before execution. No cascading deletion of command outcomes.
- No automatic command/attempt pruning. A migration trigger prevents legacy test cleanup from deleting unresolved or command-linked test records. Compact retention, privacy erasure and manual reconciliation remain operational review items before activation.
- Command identity/payload/policy/deadline are immutable. Terminal command outcomes cannot be automatically rewritten. Manual reconciliation must inspect receipt/Discord evidence and use a separately reviewed operator procedure; there is no resend/reset shortcut.
- Unknown network failures after the send boundary, including an unclassified post-boundary rate failure, are conservatively uncertain. Known pre-send rate limits use Retry-After; delays beyond TTL expire rather than retry early.

New migration: **`packages/database/migrations/0007_phase15c_commands.sql`**, with journal entry and `0007_snapshot.json`. It creates three tables, claim/lookup indexes and checks, a restricted boolean session-identity function, immutable-command trigger and test-retention trigger. Security-definer functions use fixed search paths and schema-qualified tables; PUBLIC execution rights are revoked. No user OAuth-token column is returned.

**Not applied to the real development database.** Applied only in embedded fixtures and a new disposable local PostgreSQL schema, which was removed afterward. The original seven-migration local schema remains supported by unchanged legacy paths. Do not apply the new migration or activate processing automatically. Back up/verify the intended target and review explicit role grants before a later approved activation. Existing credentials and application data were not changed.

Restricted-role tests exposed that existing joined `SELECT FOR UPDATE` statements need UPDATE privilege on at least one column of the joined provider/subscription tables. Isolated consumer fixtures grant only `UPDATE(id)` for those row locks, alongside necessary queue/settings/test rights, without auth-table access. Actual service-role provisioning remains deferred; no live grants were changed. The session validity function requires an explicit EXECUTE grant. No schema-owner credentials should be used for normal runtime.

Official semantics checked: [PostgreSQL SKIP LOCKED](https://www.postgresql.org/docs/current/sql-select.html), [security-definer functions](https://www.postgresql.org/docs/current/sql-createfunction.html), [Discord targeted guild/member endpoints](https://docs.discord.com/developers/resources/guild#get-guild-member). Actual external REST behavior with this application is not established by mocked tests.

## Remaining risks and handoff

1. **Not activated:** dashboard still uses its current local broker; no command HTTP endpoints or UI polling, runtime scheduler, automatic schema/grant application or cloud transport configuration is added. Phase 15D/F must wire the factories with the actual trusted session/fresh-authorizer and `database.withAccountLock` coordinator, preserving this phase's safe defaults. A no-op coordinator is only for synthetic tests.
2. **External verification blocked:** no real command-driven Discord sends/member checks, OAuth/install journey, YouTube/Kick starts, cloud TLS/roles, hosting soak or new external receipt was attempted. Existing normal monitoring behavior is regression-tested, not freshly live-verified.
3. **Ambiguity is deliberate:** quarantine may include an unsent request if a crash happened after the marker but before HTTP. Late receipts help manual reconciliation; terminal uncertainty remains preserved. No promise of exactly-once delivery.
4. **Operations:** no automatic tombstone pruning; capacity and privacy/erasure procedures need review before activation. Per-instance single-step processing must be integrated with graceful startup/shutdown and distributed bot ownership during later runtime preparation.
5. **Hosting remains NO-GO:** the earlier Render/Neon compute/backend availability/cost and real acceptance blockers remain. No new Redis dependency, credentials, public broker, privileged intent or cloud resource was introduced.

**Recommendation:** GO for a separately approved **local Phase 15D integration using isolated fixtures**, subject to these contracts; NO-GO for activation, deployment or release. Stop after Phase 15C and wait for owner approval.
