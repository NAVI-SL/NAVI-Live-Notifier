## Recommendation and current architecture

Prototype a **PostgreSQL-backed dashboard command/acknowledgment layer**, consumed by the bot backend. Co-host the existing bot and worker as **separate supervised processes** on one always-on host, preserving their private loopback broker and existing automatic delivery. Do not put normal livestream deliveries through the new control queue.

This removes dashboard-to-bot HTTP without exposing the broker or bot token. It does not solve always-on hosting/database cost. No reviewed provider was established as a reliable indefinitely free, no-card fit for the full workload. Remain local or use a separately approved supervised beta until hosting and real integration gates close.

Inspected actual manifests, web guild/auth/notification services and broker, bot status/sender/Gateway lifecycle, worker monitor/providers/runtime, database schema/claims/locks, deployment edge/Compose and current Phase 14D/Render reports.

| Current caller                    | Actual operation                                                                                             | Proposed replacement                                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Web `lib/discord.ts`              | Installation status via authenticated `GET /internal/guilds/:id`; timeout becomes unknown                    | Timestamped backend snapshot plus bounded refresh command; stale/unknown never means not installed.            |
| Web `lib/notification-broker.ts`  | Target channels/roles, optionally forced fresh                                                               | Typed read/refresh command and validated snapshot.                                                             |

| Web guild service                 | Better Auth session, allowed users, fresh OAuth guild-management check, allowed guilds, explicit install URL | Preserve on web for all admission and result reads. Install URL generation needs no broker.                    |

`BOT_INTERNAL_URL` only accepts HTTP loopback; existing Compose shares the edge network namespace. Neither `live_deliveries` nor `notification_test_attempts` is a general RPC queue. Reuse durable claim/uniqueness/uncertainty patterns with new additive control tables; do not overload notification records.

## Alternatives

| Architecture                                            | Benefits and costs                                                                    | Recommendation                                                                                                     |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Existing all-in-one host/edge, separate processes       | Smallest change, private broker; common host failure domain                           | Best immediate operational fit if an approved always-on host exists.                                               |
| Render web + PostgreSQL commands + co-hosted bot/worker | No public broker; web sleeping does not stop monitoring; medium additive migration    | Preferred split-host prototype, conditional on backend/database funding or verified sponsorship.                   |
| Public HTTPS broker                                     | New public security boundary, mutual authentication/replay/abuse controls required    | Not selected: preserves direct dashboard-to-bot dependency. Public shared-bearer endpoints are not the workaround. |
| Reverse WebSocket tunnel through dashboard              | Reconnect/order/queue complexity and dashboard availability dependency                | Not selected; no artificial keepalive traffic.                                                                     |
| Redis Pub/Sub/new Redis queue                           | Pub/Sub alone loses disconnected work; durable queue adds infrastructure/dependencies | Not selected; PostgreSQL already owns durability. Upstash is not required.                                         |
| Merged bot/worker Node process                          | Shared heap/event loop, credentials and failure domain; larger refactor               | Not initially justified. Co-hosting two supervised processes is safer.                                             |

```text
Browser --HTTPS--> Next.js --authenticated, guild-scoped commands--> PostgreSQL
Browser <--authorized result reads-- Next.js <---ack/snapshots------- PostgreSQL
                                                                     ^
                                                                     | outbound TLS
Always-on backend: bot + command consumer <---------------------------+
                   ^
                   | existing private broker
                worker --> existing live_deliveries --> Discord sender

Provider hooks --> restricted backend HTTPS ingress --> existing verification
```

Only verified webhook paths and minimal non-sensitive liveness need public backend ingress. Keep `/internal`, diagnostics and detailed readiness private. Without approved HTTPS ingress, actual webhook acceptance remains blocked; reconciliation polling does not establish subscription compatibility.

## Proposed command schema and protocol

**Design only; no DDL applied.**

| Proposed relation     | Fields and rules                                                                                                                                                                                                                                                                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dashboard_commands`  | UUID; schema version; allowlisted kind; guild ID; server-derived actor Discord ID and internal session reference; idempotency key; bounded validated JSON/hash; status; attempts/due/expiry; lease owner/expiry/generation; effect-start timestamp; sanitized result/error; created/completed times. Request identity/payload immutable after admission. |
| `guild_bot_snapshots` | Primary key `(guild_id,kind)`; bounded install/channel/role result, observed/expiry time, backend generation. Backend writes; authorized web reads. Never authorizes mutations.                                                                                                                                                                          |
| `backend_heartbeats`  | Instance/service identity and generation, observed time, readiness codes and bounded operational aggregates. No raw Discord bodies or credentials.                                                                                                                                                                                                       |

Initial kinds: `refresh_guild_status`, `refresh_notification_targets`, `apply_notification_settings`, `send_test_notification`. No arbitrary URL/method, SQL, Discord route or trusted pre-rendered message. Settings commands carry subscription reference, expected version and validated preferences. Tests reference current saved settings/version. YouTube/Kick registration and OAuth tokens remain with the web.

Constraints/indexes: unique `(guild_id,actor_id,kind,idempotency_key)`; same key with changed payload rejected; composite guild/subscription binding; size/kind/status checks; due-work partial index; expired-lease index; actor/guild result lookup; positive attempts/generation and valid TTL. States: `pending`, `leased`, `succeeded`, `failed`, `expired`, `cancelled`, `uncertain`. Existing live-delivery states stay unchanged.

Claim bounded batches using short `FOR UPDATE SKIP LOCKED` transactions; commit owner/generation/lease before external I/O. Complete conditionally against that owner/generation. Do not hold SQL row locks across Discord HTTP. PostgreSQL documents this locking mode as appropriate for queue-like consumers. [SELECT locking](https://www.postgresql.org/docs/current/sql-select.html).

Prototype bounds: 16 KiB command, 256 KiB result with item limits, at most three command consumers, per-guild read coalescing, 5-second active polling backing off to 30 seconds idle. Return `202` plus random ID; bounded browser polling runs only for pending user actions and stops on completion, logout, navigation or timeout. A browser timeout is not a failed operation: reload the same request. Cap outstanding work and rate-limit admission/results per actor/guild. Read coalescing never exposes another actor's operation result. These are proposed values requiring measurement.

Optional later `LISTEN/NOTIFY` is a wake-up hint, not durability: rescan rows after reconnect. Put no secrets or payloads in notifications, visible to DB users; maintain a dedicated direct session if used. It cannot replace the table. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html).

## Authorization, isolation and mentions

1. Web validates actual Better Auth session, allowed identity, **fresh OAuth guild authority**, beta scope and request origin before admission. Browser actor IDs, guild IDs, destinations and claimed permissions are untrusted. Preserve secure cookies, state checks and `identify guilds` scopes.
2. Results require current session/guild authorization and actor ownership too; knowing a UUID is insufficient. Store only an internal session reference, never a cookie, access/refresh token, bot token or general bearer in queue JSON. No browser database credentials.
3. Backend rechecks expiry, beta scope and session/actor validity before delayed mutations/tests through a narrowly granted DB function exposing only necessary identity/revocation metadata. Do not grant broad OAuth-table access or distribute the auth encryption secret. Any security-definer function needs a reviewed fixed `search_path`, restricted EXECUTE grants and no dynamic SQL.
4. Revalidate current actor management permission through targeted official Get Guild Member, guild roles and owner identity. Calculate owner/Administrator/Manage Guild using integer bitsets. Fail closed on missing membership, denial, API failure or rate limit; retry only within short command TTL. Read-only absence may report not installed; mutation/test requires installed bot. Cached snapshots cannot authorize execution.
5. Reload subscription/settings/version, verify destination channel and role belong to the guild, and apply existing effective bot role/channel-overwrite permissions, Administrator, Embed Links and Mention Everyone checks immediately before effects. Permission revocation cannot be atomic with Discord; keep the check-to-effect window short and test revocation while queued.
6. SQL operations retain guild dimensions/composite constraints. Web role cannot claim work, forge results or edit live deliveries; backend command role cannot read OAuth tokens. Grant narrow function/column rights, not schema-owner credentials. Verified TLS is mandatory.

Discord documents targeted member retrieval separately from member enumeration, which explicitly requires the privileged member intent. Keep Gateway **Guilds only**; real targeted REST compatibility with the beta app must pass before acceptance, rather than enabling privileged intents preemptively. [Discord guild endpoints](https://docs.discord.com/developers/resources/guild#get-guild-member).

Existing isolation is application authorization plus constraints, not verified RLS. Optional RLS needs trusted transaction context, pooled-connection reset and owner-bypass tests. A browser-provided SQL session variable or shared DB login is not tenant authentication. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

Explicit saved role/everyone selection and safe `allowed_mentions` remain authoritative. Templates and metadata cannot manufacture mentions. Preview/test never ping everyone. Role/channel deletion and bot removal remain explicit configuration errors, not uncontrolled retries.

## Transaction boundaries and uncertainty

- Reads can retry/coalesce while unexpired; show `observed_at` and stale/unknown status.
- Settings: backend verifies actor/destination, then commits the existing versioned settings save **and command completion in one database transaction**. Stale versions cannot overwrite. Lost acknowledgment resolves by re-reading command/version. A later UI refresh error cannot reverse a successful commit. Repository transaction support must be added/tested; a new queue table alone does not provide this.
- Tests: reserve `notification_test_attempts` and enqueue atomically. Persist an effect-start marker before invoking the existing sender; retain the original request ID/nonce. Record a validated Discord receipt with ledger/command outcome transactionally when possible. The current sender returns `status: sent`, not a durable message ID; receipt support is a proposed interface change.
- Expired lease before possible side effects permits bounded retry. Once a send might have started, interruption/lost response or receipt-commit failure becomes **uncertain**, never automatic resend. A crash after the marker but before HTTP may conservatively quarantine an unsent request. A stale consumer cannot overwrite another generation; generation fencing cannot stop an HTTP request already accepted by Discord.
- Keep automatic notification uniqueness `(session_id,guild_id,channel_id)`, claim/route locks, settings version and activation/freshness checks, LIVE revalidation, nonce enforcement, Retry-After and interrupted-send quarantine. No second consumer handles these rows. Preserve historical/uncertain records; never regenerate old streams during cutover.
- Discord is not exactly-once. Nonce support is an additional bounded defense, not indefinite deduplication. Retain compact idempotency tombstones when pruning large results. Suggested read-result TTL is 24 hours, diagnostic result retention seven days; mutation/test dedupe and unresolved outcomes require a separately reviewed retention policy. Never routinely delete uncertain outcomes.

## Co-hosted backend deployment

Co-hosting **can** preserve monitoring/delivery, subject to tests and host support. Use real supervision/init, one bot owner, private readiness before worker/command admission, and a shared bot REST limiter/sender. Separate processes retain scoped secrets and reduce refactoring. Do not build a single shared environment bag or a second bot connection.

Shutdown order: stop command admission and worker scheduling, abort/drain permitted I/O, persist incomplete state, stop worker, then Gateway/broker, then DB pools. Existing bot/worker watchdogs are 10/30 seconds; allow a larger host grace period. Restart with backoff/jitter and report degraded readiness if either process fails. Current Gateway lease is host-local: add a distributed owner lease/generation or enforce stop-before-start for host overlap. Worker leader locks do not automatically fence Gateway sessions; active/active hosting is out of scope.

**YouTube:** `youtubePollInterval(N,7200)` reserves 20% and assumes four units/check: N=1 gives 60 s, N=5 **300 s**, N=10 **600 s**. At N=5/10 the routine upper-budget model is about 5,760 units/day, with reserve for confirmations/hints/retries; actual calls depend on candidate batches. List costs and actual project quotas must be checked; do not invent a search-based scale-up. [Official quota table](https://developers.google.com/youtube/v3/determine_quota_cost).

**Major capacity risk:** delivery suppresses streams older than **600 s**. Ten YouTube sources already reach that poll interval: missed webhook plus scheduler/API/sequential-processing delay can exceed freshness admission. Ten-source all-YouTube low-latency coverage is **unverified** even if RAM is sufficient. Prototype this boundary; choose a lower YouTube cap or separately approved quota/discovery plan before promising coverage. Do not remove freshness suppression to hide it.

**Kick:** ten sources give 14,400 once/minute stream polls/day, about 960 identity refreshes/day, plus hourly subscription inventory when enabled, confirmations/retries and token/key requests. Low average throughput does not prove endpoint quota/headroom; use actual rate-limit feedback.

**Neon Free blocker:** current pricing documents 100 CU-hours/month/project and default 0.25 CU. Frequent scheduling/commands would keep compute active: 720 h × 0.25 = **180 CU-hours/30 days**, 186 over 31 days. This exceeds Free before scaling. At displayed Launch rates, 180 × US$0.106 = **US$19.08 compute alone**, excluding storage/backend/other charges; not spending authorization. Current pricing lists **1 GB storage**, while the older official FAQ used in the Render report listed 0.5 GB. Preserve that report as dated evidence; confirm actual account entitlements and use the conservative storage bound pending confirmation.
