## Existing security boundaries

`apps/web/src/lib/guild-service.ts` disables the session cookie cache, derives the Discord identity from the server-authenticated user, checks allowed users, retrieves OAuth credentials server-side, and filters owner/Administrator/Manage Guild. `authorize` forces fresh guild retrieval and checks optional beta scope. `runtime.ts` serializes token refresh through PostgreSQL account locks. Protected requests cannot trust a browser guild ID. Existing beta scope has a **five-guild maximum**; ten-guild sizing is not permission to change it.

`auth-factory.ts` uses encrypted OAuth account tokens, database state with cookie binding, exact callback `${WEB_ORIGIN}/api/auth/callback/discord`, secure production cookies, trusted origin and disabled account linking. `notification-http.ts` checks origin on mutations and validates content type/size. These controls remain web responsibilities, including future result polling.

The bot currently trusts a private authenticated service, **not a user OAuth identity**: broker requests do not carry a requester/session for actor revalidation. It independently validates guild/channel/role data, bot effective permissions (role union, channel overwrites, member overwrite, Administrator, timeout), config, payload and safe mentions. Its token stays with the bot. Shared Discord REST rate handling uses bounded timeouts, no automatic REST retries and sanitized rate metadata. A database queue changes the trust boundary: delayed execution needs actor/session binding and expiry, not just an inserted guild ID.

Database isolation is repository guild filters, composite subscription/settings relationships and role grants; existing RLS is not claimed. The web role currently reads auth/provider/config tables; the worker role has monitoring rights without OAuth-table access. A new command consumer needs new narrow rights rather than web credentials or unrestricted auth access. Current bot environment has **no DATABASE_URL**; giving the consumer a scoped database identity is a planned change requiring config work.

## Existing durability to reuse

`packages/database/src/monitoring.ts` transactionally claims pending due work using `FOR UPDATE SKIP LOCKED`, increments attempts and marks sending. Interrupted sending older than 120 seconds becomes uncertain. Completion uses status/expected-attempt conditions. Schema uniqueness is `(session_id,guild_id,channel_id)`. The monitor confirms LIVE again, reloads settings/version, respects freshness/activation and provider cooldown, and separates safe retry from ambiguous delivery. Preserve all of this.

`notifications.ts:save` obtains the route advisory transaction lock and versioned write in one transaction and returns the committed row; a later read cannot turn that save into failure. The same route-lock namespace coordinates settings and live sending. A command implementation must keep that lock order/namespace and make settings plus acknowledgment one outer transaction; the present repository cannot simply be called then acknowledged in another commit.

`claimTest` serializes test reservation, enforces saved version and a 30-second per-guild test cooldown, and uses unique `(guild_id,request_id)`. The bot derives its nonce from guild/request ID. The sender currently discards the Discord message response and returns only sent status. Test-ledger pruning removes rows older than seven days, including unresolved states. **Future migration must protect unresolved/command-linked rows and compact dedupe evidence**; do not silently reuse pruning unchanged. Nothing is pruned or reset by this audit.

## Findings and migration risks

| ID  | Severity                    | Finding and required disposition                                                                                                                                                                                                      |
| --- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A01 | Major blocker               | Separate dashboard cannot reach loopback broker. Keep local implementation until tested database adapter cutover; never expose broker publicly.                                                                                       |
| A02 | Major design risk           | Queue insertion is not execution authorization. Bind requester/session, verify expiry and current actor management authority, and fail closed on backend API failure.                                                                 |
| A03 | Major design risk           | Separate settings commit and command ack could misreport outcome; separate test reservation/enqueue could orphan work. Require atomic transactions and idempotency.                                                                   |
| A04 | Major design risk           | Lease retry after Discord ambiguity can duplicate messages. Require effect boundary, attempt fencing and uncertain outcome; no exactly-once claim.                                                                                    |
| A05 | Major migration requirement | Existing seven-day test pruning and response-without-message-ID are insufficient as an indefinite command reconciliation contract. Preserve unresolved evidence and add a safe test receipt interface during approved implementation. |
| A06 | Major release blocker       | Render/Neon Free continuous-runtime limits and unverified backend eligibility/capacity remain; transport cannot resolve them.                                                                                                         |
| A07 | Major security requirement  | Production web still requires broker URL/secret, release preflight compares them across services, and private health tools assume one host. Make validation/probes transport-specific later, never globally permissive.               |
| A08 | Minor/operational           | More status polling can amplify existing OAuth/Discord rate pressure. Bound polling, honor Retry-After, coalesce metadata reads, preserve fresh authorization and do not retry enqueue under new IDs.                                 |

**A09 — major migration requirement:** `scripts/check-release.ts` also compares complete web/worker DATABASE_URL strings. Distinct least-privilege logins for the same DB legitimately differ. Later mode-aware preflight must verify intended canonical endpoint/database identity without requiring identical credentials or printing URLs.

No new critical exploit is asserted from source review alone. These are concrete blockers and design hazards, not claims of a successful new transport or penetration test.
