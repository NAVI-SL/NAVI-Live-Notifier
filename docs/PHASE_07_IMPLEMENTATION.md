# Phase 7 — reliability, duplicate prevention and recovery

Implemented 2026-10-17 (Asia/Colombo), under the user's explicit Phase 7 instruction. Phase 8 is not started or authorized. This extends the existing PostgreSQL queue, independent worker and bot-owned Discord sender; no dashboard feature or additional platform was added.

## Reliability changes

- **Durable admission and state:** retained the unique session hash and unique `(session_id,guild_id,channel_id)` constraint. Normal states are `pending`, `sending`, `sent`, `failed`, `uncertain`, with `suppressed` retained for intentionally ineligible work. New database checks reject negative attempt counts and invalid settings versions. Completion updates from the worker also match the claimed attempt number, so a stale completion cannot finish a later attempt.
- **Concurrent ownership:** transactional `FOR UPDATE SKIP LOCKED` claims remain authoritative. Global monitor leadership and per-subscription PostgreSQL session locks coordinate monitoring and send initiation with saved configuration changes. Leadership is now checked after external observation and before dispatch, as well as route-lock checks immediately before the broker request. No database transaction spans provider/Discord HTTP.
- **Restart and ambiguity:** pending work survives reconstruction. A `sending` row older than two minutes is quarantined as uncertain, never automatically retried. A lost broker response, malformed success response, unexpected acknowledgment or database failure after a successful POST similarly cannot trigger a blind resend. At-most-one logical admission is not a permanent exactly-once Discord guarantee.
- **Safe retries:** pre-send coordination/transient failures can retry with bounded exponential delays (5 attempts maximum). The broker explicitly identifies known failures occurring during permission/target preflight as safe to retry. Definitive 429 replies honor decimal seconds and HTTP-date `Retry-After`; terminal destination/auth/payload rejections fail closed. Unknown or post-message network/5xx failures remain uncertain. The existing Discord REST client still has zero automatic POST retries.
- **Current destinations:** the bot rechecks guild/channel/role permissions on each live send. Removed bot, missing channel, revoked permissions and invalid selected role fail with safe, useful categories. The worker rechecks enabled/current settings, ownership, expiry and subscription/settings activation times; disabling and re-enabling cannot revive a pre-activation queued alert.
- **Webhook recovery:** migration `0005_phase07_reliability.sql` adds `monitor_sources.hint_version`. A committed receipt increments that generation. Discovery merges into a locked current row; completed polling replaces candidates only when the generation it observed still matches. A concurrent hint, including a change to an existing video ID, preserves both its candidate and wake-up. Receipt deduplication and bounded candidate rotation remain persistent.
- **Reconciliation and sharing:** official polling still recovers missed callbacks, with one shared platform source distributed to eligible Discord guilds. LIVE is rechecked before sending; shared fan-out proof expires after 30 seconds during long batches. Repeated live observations, title changes and offline/reconnect observations with the same session key do not create new normal deliveries.
- **Logging:** source checks/errors, safe delivery outcome/error categories, attempt counts, lifecycle failures and shutdown events are structured JSON. No raw provider error body, credential, callback MAC URL, access token or session cookie is logged. Google's documented `API_KEY_INVALID`/`API_KEY_EXPIRED` errors now classify as rejected credentials with cooldown rather than generic unavailability.

### Session and reconnection policy

YouTube session identity remains its video ID; reconnecting the same broadcast never re-notifies. Kick session identity remains stable broadcaster ID plus canonical UTC `started_at`, preserving Phase 6 deduplication history. An interruption returning the same start time is the same session; a genuinely different start time is a new logical session and may notify if fresh and eligible. NAVI does not guess whether two different provider sessions are the same human broadcast. Several hours live cannot bypass the persistent session key or ten-minute new-start eligibility window.

### YouTube capacity correction

Phase 6 audit M05 identified fixed per-source polling above the daily budget. The worker now computes a shared cadence for all active YouTube sources:

`intervalMs = max(60000, ceil(86400000 * sourceCount / max(1, floor(dailyBudget * 0.8) - sourceCount * 192)))`

The 192 units/source/day cover channels + playlist discovery every 15 minutes. Twenty percent of the worker budget remains for confirmations, hints and retries. With ten sustained sources and the default 7,200 allowance, nominal video polling becomes **225 seconds/source**, about 3,840 video calls plus 1,920 discovery calls/day, leaving 1,440 units. The ten-second scheduler can make actual timing slower. Due sources are processed oldest-first, with a stable tie break. Up to 100 candidates rotate through batches of 50; known-candidate latency therefore depends on rotation as well as cadence.

This is budget-aware personal scheduling, not guaranteed detection coverage. Web registration can consume the same Cloud project's quota outside the worker counter. Webhook bursts, errors, operator-selected larger source caps and downtime can still exhaust headroom; the persistent hard budget stops requests. If metadata alone exceeds the allocation, cadence degrades severely rather than evading quota. YouTube's feed/playlist discovery and Premiere classification gates from Phase 6 remain unresolved. No undocumented endpoint or scraping was added. [Official quota costs/reset](https://developers.google.com/youtube/data/determine_quota_cost).

## Health and graceful shutdown

- **Bot:** authenticated loopback `GET http://127.0.0.1:4001/internal/health` performs a current Discord identity REST request. It returns `200 {status:"ok"}` or a redacted degraded `503`; it never sends a message. It uses the existing broker bearer secret and does not trust an old identity cache.
- **Worker:** authenticated loopback `GET http://127.0.0.1:4100/internal/health` returns worker/database/bot and YouTube/Kick summaries with `Cache-Control: no-store`. Unauthenticated requests get 401. It is independent of public webhook configuration. Health is available only while the enabled worker listener runs.
- Bot health is refreshed during monitor ticks at most once per 30 seconds. Platform health summarizes recent active-source checks as `ok`, `degraded`, `idle` or `not_configured`. Idle means there are no observed active sources, **not that credentials or livestream behavior have been independently certified**. Failed/stale checks degrade readiness; missing configuration is disclosed. No health endpoint promises webhook reachability or message delivery.
- Startup checks the required monitoring schema before announcing readiness. Missing schema, database access or port binding fails safely and closes database pools. A missing provider credential can leave the other provider usable, but is visible in health/errors.
- One runtime tick runs at a time. SIGINT/SIGTERM stops admission, clears the interval, aborts provider/broker I/O, drains the in-flight tick, closes ingress connections and closes database pools. Requests already initiated remain potentially accepted. A 30-second shutdown watchdog exits with failure if draining stalls; durable `sending` rows then recover as uncertain. Windows forced termination/host crashes cannot run normal signal cleanup, so durable recovery remains essential.

Keep `/internal/*`, bot broker and databases private. Expose only `/webhooks/*` through the narrow HTTPS proxy. No frontend health/dashboard controls were introduced. Existing channel/role validation, explicit `allowed_mentions`, webhook HMAC/RSA checks, body limits and guild authorization remain in place. [Discord rate limits](https://docs.discord.com/developers/topics/rate-limits), [message nonce and mentions](https://docs.discord.com/developers/resources/message).

## Remaining risks and manual acceptance

Phase 6 audit disposition: **M02/M03 corrected** with focused concurrency/activation tests; **M05 addressed** by computed cadence and budget-allocation tests, with actual workload measurement still required. **M01 partially closed:** schema deployed and Kick/Discord read-only authentication verified, but YouTube/live acceptance still fails or remains pending. **M04 remains open:** official YouTube discovery/Premiere feasibility needs controlled streams. N01 current scope pointers are reconciled; N02 has lifecycle/unit/actual database-connection coverage but still needs OS/process crash acceptance; N03/N04 operational/advisory limits remain open. This does not retroactively mark the Phase 6 audit PASS.

1. **Correct the YouTube key privately:** select the intended Google Cloud project, confirm YouTube Data API v3 is enabled and use a valid appropriately restricted server-side key in the existing worker service configuration. Do not paste its value into documentation/chat. Rerun connectivity; an application code change cannot repair `API_KEY_INVALID`.
2. **Do not equate API access with live delivery:** real scheduled/unscheduled/long-scheduled YouTube streams and Premiere experiments, actual Kick signed start events, TLS callback/lease verification and two-guild received-message/role inspection remain required. No real automatic livestream notification has been verified here.
3. **Deployment:** keep monitoring disabled until the owner chooses the intended enabled sources/destinations, validates the bot broker match and configures HTTPS webhooks where desired. Polling can operate without callbacks but cannot guarantee arbitrary YouTube discovery.
4. **Process recovery:** verify real enabled workers on the intended host, stop the website, kill/restart a worker during delivery, exercise competing worker processes, database interruption and revoked Discord access. Unit/runtime and database-connection tests do not prove OS/container signal handling or actual crash outcomes.
5. **Uncertain outcomes:** inspect the actual Discord channel before any future manual recovery decision. There is no automatic resend/resolution UI. Discord nonce protection is only a recent-window safeguard; no permanent exactly-once promise is made.
6. **Existing operational limits:** moderate tooling advisories, upstream subscription garbage collection, provider-data/candidate/hash retention review and backup lifecycle remain as documented. No new dashboard, platform, billing or Phase 8 work was introduced.
