## 4. Security findings

**No newly confirmed critical application defect was found in the tested scope.** This is bounded validation, not a penetration-test or compliance certification.

- Missing synthetic session, revoked database session, disallowed manager, cross-guild result access, invalid kinds, extra credential-shaped payload fields and cross-origin admission are rejected. Payload/result DTOs omit session references, raw payloads, owners and requester internals.
- Synthetic sensitive exception text is absent from command results and structured logs. Real tokens, cookies and connection URLs were never printed. Fault diagnostics intentionally suppress raw database exceptions.
- Effective web role cannot UPDATE/claim commands, write snapshots or delete attempts. Effective bot role cannot SELECT OAuth session/account tokens, create tables or delete commands. The narrow identity function returns a boolean and works with explicit EXECUTE without auth-table SELECT.
- Normal notification sender, safe mentions and allowed_mentions behavior are unchanged and regression-tested. Webhooks/authentication/retry handling remain covered by existing simulated suites; no real webhook or Discord permission grant is asserted.
- Loopback-only broker remains unchanged. All 14 isolated edge checks pass, including private-route rejection, host/header handling, body limits, local auth throttling and safe OAuth logs. This does not certify a future cloud edge configuration.

**Role-test limitation:** temporary roles are NOLOGIN, exercised through effective `SET ROLE` startup options using the local administrative connection. This proves SQL privilege checks under those effective roles; it does not prove separate cloud login credentials, Neon role provisioning, RLS or resistance after compromise of the administrative test login. Production services must use their own restricted login identities, never this test arrangement.

## 9. Rollback readiness

**PASS locally:** pause admission while retaining postgres mode, continue scoped status reads, preserve pending/uncertain rows and keep immediate DB-only disable. The fixture verifies no replacement command or broker fallback. Local HTTP mode, direct sender compatibility and default flags remain covered by the full regression suite.

Follow the Phase 15D procedure: pause new admission; drain only safe approved work or stop the consumer; recover/expire unstarted commands and quarantine marked outcomes; retain attempts, receipts and idempotency keys. Do not drop migration 0007, reset uncertain rows, replay a test through HTTP, or restore stale data over newer evidence. Keep a maintenance/status instance until outcomes are reconciled. HTTP rollback is available only where the old private broker is actually reachable; remote Render must remain in maintenance/read-only mode rather than using localhost fallback.
