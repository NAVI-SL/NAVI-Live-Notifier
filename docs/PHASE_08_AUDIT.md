# Phase 8 audit — security, deployment and production configuration

Audit date: **2026-10-18 (Asia/Colombo)**.

**Recommendation: FAIL / HOLD for production acceptance. Automated application baseline: PASS.** All **249 tests in 23 files**, TypeScript, linting, formatting and native production builds pass. Eight isolated production Next.js HTTP checks and actual read-only YouTube/Kick/Discord checks also pass. Docker runtime/TLS, external PostgreSQL, backup restoration and production end-to-end acceptance remain unverified or blocked.

Findings: **0 critical, 3 major acceptance/operational gaps, 4 minor improvements or residual risks**. No new acceptance-blocking application-code defect, credential disclosure or tenant-authorization bypass was demonstrated. The major findings concern evidence and unfinished operational setup; they are not presented as newly reproduced application exploits. Locally reviewable preparation has been delivered, but “completed Phase 8” must not be interpreted as a verified production deployment.

## Scope and method

Reviewed the approved direction, canonical development roadmap, architecture/schema/security/decision records, Phase 7 audit, Phase 8 implementation report, deployment guide/checklist, progress and the later Gateway/YouTube-notification contracts. Reviewed current web auth/guild/install/settings boundaries, bot Gateway/REST/broker, worker monitoring/webhooks/lifecycle, shared configuration/database code, migrations through `0006_youtube_embed_mentions.sql`, manifests, ignore rules, Docker/Compose/Nginx configuration and regression tests. Older historical proposals do not override the implemented PostgreSQL queue, current bot Gateway or explicit default-off YouTube everyone exception.

Environment: Windows, Node **25.3.0**, npm **11.15.0**, Docker Compose **5.6.0**. The Dockerfile targets Linux/Node 24; the native Windows runs do not certify that image. Checks requiring local networking ran outside sandbox restrictions. No application source/configuration fixes, dependency upgrades, migrations on application tables, production credential changes, DNS/Portal changes, real messages or public deployment were performed. No Phase 9 work began. Only this maintained audit document was added; temporary ignored diagnostic probes were used for evidence and removed afterward.

Evidence is separated into maintained automated tests, actual isolated SQL/HTTP, native production server behavior, actual read-only external APIs, static configuration review and unexecuted production acceptance. Official [Discord OAuth2](https://docs.discord.com/developers/topics/oauth2), [Better Auth security](https://better-auth.com/docs/reference/security), [Docker secrets](https://docs.docker.com/compose/how-tos/use-secrets/), [Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/), [restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/) and [PostgreSQL backup guidance](https://www.postgresql.org/docs/17/backup-dump.html) were consulted alongside the installed Next.js self-hosting documentation. External guidance supports configuration review, not an inference that deployment succeeded.

## Major findings

### M01 — Executable container/TLS and real deployment acceptance is incomplete

**Major acceptance gap; no demonstrated container code defect.** `compose.production.yaml` parses, but the Linux Docker engine is unavailable and the image build fails before execution. At the default local-review paths, the production secret directory, certificate and certificate key do not exist. Monitoring is disabled and public webhook origin/secret are absent. No hosting/domain/production database has been selected, consistently with the owner's instructions.

Consequently, Linux/Node 24 runtime dependency installation, nonroot file access, read-only cache behavior, Nginx syntax/TLS/rate limits, shared namespace DNS, secret mount ACLs, signal forwarding and restart behavior remain untested. Actual API authentication success does not demonstrate production OAuth/install, external signed callbacks, website-independent monitoring or two-guild received notifications.

**Required correction:** restore Docker locally, privately create isolated review material, build/run the review project and execute the deployment checklist. Test edge-container replacement with coordinated app recreation, website-off monitoring, SIGTERM/forced restart and temporary network outages using reviewed test destinations. Obtain the owner's separate infrastructure approval before selecting/publishing a host or changing DNS/credentials. Record actual browser/provider/message evidence without exposing codes or cookies.

### M02 — Actual database migration, persistence and disaster recovery remain unverified

**Major acceptance/operations gap.** Current PostgreSQL connections are refused. The audit cannot verify actual schema version, migration 0006, runtime-role grants, connection-level coordination, durable volume behavior or encrypted backup restoration. Embedded SQL/role tests pass and must not be relabelled as a deployed PostgreSQL result.

The latest YouTube enhancement requires `notification_settings.mention_everyone`; the worker now checks it at startup and web notification queries also require it. The earlier update recorded migration 0006 as unapplied, and this audit cannot inspect a running server to close that gate. Backup encryption, scheduling, offsite storage and restore testing are instructions, not configured jobs or executed recovery evidence. Claimed RPO/RTO remain proposed.

**Required correction:** restore the intended development database, privately verify the target, review/apply additive migrations through 0006, rerun isolated external PostgreSQL tests and test actual nonsuperuser runtime roles. Recreate/restart containers without losing data. Configure the approved backup mechanism and restore a verified archive into a separate database, including the auth encryption secret and migration journal. Keep monitoring stopped after an old restore until already-sent/deduplication state is reconciled. Never reset the active volume as an audit shortcut.

### M03 — Unattended operational detection and TLS lifecycle are not configured

**Major operational release gate, already disclosed by the implementation guide.** Log rotation and health probes exist, but no private log/alert destination, operator notification path, certificate renewal/expiry checks or backup-completion monitoring is configured. `deployment/nginx.conf:6` intentionally suppresses request error logs; safe access records provide only method/status/duration. That protects callback material but cannot by itself diagnose/alert on failed renewals, stalled monitoring, uncertain deliveries or repeated API failures.

`unless-stopped` handles exited processes; an unhealthy process does not automatically restart. This is an accurate documented policy, not evidence that alerts or remediation exist. Docker restart and Compose health/dependency semantics must be verified separately on the intended runtime. [Official restart behavior](https://docs.docker.com/engine/containers/start-containers-automatically/).

**Required correction:** select an owner-approved, potentially local/low-cost monitoring mechanism, configure redacted health/log/certificate/backup alerts and deliberately trigger failures to verify delivery and an operator response. Do not replace conservative uncertain handling with blind restarts/resends. Keep URI/query/header/body redaction and confirm that the selected collector cannot capture secrets. No paid monitoring purchase is required or authorized by this finding.

## Minor findings and residual risks

### N01 — Four moderate dependency findings remain

Current production audit lists `@esbuild-kit/core-utils`, `@esbuild-kit/esm-loader`, `drizzle-kit` and `esbuild`; npm's offered fix is a breaking Drizzle Kit 0.18.1 downgrade. No high/critical finding was reported. The tooling chain remains in npm's production classification; excluding dev dependencies alone does not establish its absence. No affected development tooling server is configured for exposure, but that is mitigation, not remediation.

**Correction:** test a compatible upstream resolution or document owner acceptance and exposure controls; scan the actual Linux runtime image when available. Do not force the proposed downgrade merely to obtain a green report.

### N02 — Release images are not immutable or image-scanned

`Dockerfile:2` and the dependency/runtime stages use `node:24-bookworm-slim`; Compose uses `nginx:stable-alpine`, `postgres:17-alpine` and the default `navi:local-review` tag. The npm lockfile constrains packages but not moving base-image contents. This is explicitly a review default in the guide, not a pinned production artifact.

**Correction:** resolve approved image digests, assign an immutable application release tag, retain previous compatible images and scan/record the built Linux image before release. Native build success does not establish OS-package vulnerability status or Node 24 execution compatibility.

### N03 — Private health has intentionally narrower coverage than full service readiness

Source review: `deployment/healthcheck.mjs:26` checks only `auth_user` for web database access. It does not prove that registration/settings queries or the new notification column are usable. Bot health calls REST identity, so it can remain healthy while the Gateway is disconnected. Worker readiness has stronger required-provider/schema checks, but its green status does not prove public webhook reachability or actual delivery.

**Correction:** strengthen a private startup/readiness gate for required web schema and expose/check Gateway readiness separately, or retain explicit limited probe labels and enforce a successful migration/runtime verification gate before traffic. Add focused incomplete-schema/disconnected-Gateway tests if health is expanded. This is a source-reviewed coverage limitation, not a reproduced live outage or tenant bypass; the guide already documents some limits.

### N04 — Strict script CSP remains deferred

The edge provides `base-uri`, `object-src` and `frame-ancestors` restrictions, but no nonce/hash-based script policy. React escaping, fixed template variables and mention/URL validation pass regression tests; no XSS exploit was demonstrated. The implementation correctly calls its CSP partial.

**Correction:** assess a Next-compatible strict CSP before public expansion, or explicitly accept the residual risk for the allowlisted stage. Preserve the dashboard's same-origin Referrer-Policy needed by the install form when adjusting headers. Do not break OAuth/install navigation with an untested blanket policy.

## Unverified production assumptions

- An owner-approved host/domain, production secret store, TLS certificates, actual file ownership/ACLs and DNS do not yet exist in this reviewed setup. Successful development environment validation is not production provisioning.
- Actual Developer Portal redirect allowlist, Guild Install settings, Code Grant toggle, API key restrictions and runtime guild/channel/role permissions were not revalidated through the Portal. Read-only identity/API access does not prove those settings.
- Public HTTPS callback verification, renewal, provider retries/key rotation, YouTube coverage/Premiere discrimination, latency and sustainable quota/load remain manual evidence gates.
- Same-host PostgreSQL bridge transport is documented; external managed PostgreSQL needs verified TLS/CA, network policy and session-preserving advisory locks. No production TLS database connection was tested.
- Named-volume persistence, actual nonsuperuser roles, backup encryption/key recovery, offsite retention and a timed restore were not tested. There is no demonstrated RPO/RTO or uptime SLA.
- Gateway ownership does not span Windows, Docker's VM or other hosts; one bot replica per token remains an operator requirement. Shared edge namespace recreation and real Linux signal handling remain unverified.
- Exact-value browser scanning is bounded evidence, not certification of all transformed secrets, image layers, server logs or source-control history.
- Account allowlisting and private bot mode remain current safeguards. Public-user expansion, policy/retention decisions and accepted residual risks need separate review/approval.

## Required corrections and final recommendation

1. Close **M01** with actual local container build/TLS/ingress/process tests and redacted real integration evidence. Do not treat Compose parsing, native HTTP or provider authentication as deployment success.
2. Close **M02** with current real migrations/roles/persistence, independent PostgreSQL tests and an isolated encrypted-backup restore drill, including post-restore deduplication precautions.
3. Close **M03** with verified private operational alerts and certificate/backup lifecycle monitoring; preserve secret redaction and safe uncertain outcomes.
4. Resolve or explicitly accept **N01–N04**, with pinned/scanned releases, appropriate readiness coverage and a reviewed browser-security policy. Repeat relevant checks after corrections.
5. Keep public provisioning, DNS, credentials and release approval as explicit owner actions. This audit authorizes no production infrastructure changes and no Phase 9.

**Final assessment: automated baseline PASS; full Phase 8 production acceptance FAIL / HOLD.** The reviewed preparation and security corrections have useful evidence, including real read-only platform authentication and native protected-route behavior. The remaining deployment/data-recovery/operations gates prevent a production-ready claim. No real deployment, received automatic Discord notification or backup restoration was verified during this audit.
