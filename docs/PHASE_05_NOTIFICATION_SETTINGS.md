## Implemented behavior

Each registered streamer has one independently configured ordinary Discord text destination, message template, optional role mention and enable preference. YouTube and Kick entries can use different channels in the same server. This is a minimal configuration record attached to the existing guild subscription; it does not create a second provider registry or implement the broader future multi-destination/defaults/pause/embed proposal.

The protected Notifications page loads registered subscriptions and saved settings. The browser then requests freshly verified Discord channels and roles from the server. Only channels where the bot currently has View Channel and Send Messages are selectable. Only mentionable, unmanaged roles other than @everyone are selectable. Loading, empty, missing-channel/role, bot-removal, success, stale-version, expired-session, API/rate and uncertain-send states have visible guidance. Existing settings remain readable when the bot is unavailable.

Templates accept exactly `{streamer}`, `{platform}`, `{title}` and `{url}`. Validation permits 1–1500 trimmed characters, rejects unknown/unbalanced braces, raw Discord user/role mention syntax, @everyone/@here and invalid controls. Preview is server-authorized plain text using registered identity, a canonical channel URL and an explicitly **sample** title. It sends nothing. The labelled test renderer caps the entire message to 2000 UTF-16 code units without splitting a Unicode code point. Long substitution results can be truncated, as disclosed in the form. It performs no executable template evaluation or recursive substitution.

Saving returns the committed configuration and version directly; the UI does not depend on a second list fetch to display a successful save. Tests require saved, unchanged settings. The separate Test Notification button sends a real `[NAVI TEST — SAMPLE DATA]` message and can mention the explicitly selected role, even when the notification preference or streamer subscription is disabled. The UI discloses this distinction. A saved enable preference is preparation for future delivery, **not active monitoring**. Future automatic delivery must require both the subscription and notification preference and establish the separately designed activation/baseline rules.

Ordinary saves and previews validate the channel/role against a fresh bot-side snapshot. If a destination becomes inaccessible, a role is deleted/unmentionable, or the bot is removed, the operation fails safely with repair guidance. A separate restrictive **Disable saved notifications** action accepts only the expected version, preserves server-owned destination/template/role values and sets enabled=false. It requires fresh user authorization but can work without the bot: disabling cannot create a destination or authorize a send.

## Architecture and official Discord contract

The Next.js web process owns Discord user sessions, fresh server-manager authorization, settings persistence, preview and test-request admission. The bot remains the only holder of `DISCORD_BOT_TOKEN`. Its existing credential-protected loopback broker now additionally lists eligible channels/roles and executes explicit tests. The worker remains idle. There are no provider polls, webhook subscriptions, event/session detection, automatic sends, generic jobs or outbox dispatcher.

The bot uses Discord API v10 through the existing discord.js REST client, with eight-second request timeouts, zero configured retries and rejection of SDK rate-limit waits. It obtains its user ID through `/users/@me`; guild state is re-read with guild, guild channels, guild roles and its own guild-member endpoints. It calculates permissions using BigInt: base @everyone plus member roles; Administrator bypass; everyone overwrite; combined role deny/allow; then the member overwrite. Timed-out members are not sendable. Only type 0 ordinary text channels qualify; threads, announcement channels, voice, forums and DMs remain excluded. No Gateway connection or privileged member-list intent is introduced.

References verified on 2026-10-17: [Discord permissions and overwrites](https://docs.discord.com/developers/topics/permissions), [guild resources/channels/roles/member](https://docs.discord.com/developers/resources/guild), [create message and allowed mentions](https://docs.discord.com/developers/resources/message#create-message). The existing installation permission integer **19456** remains unchanged; the plain-text test path needs View Channel and Send Messages and does not request Administrator, Manage Roles or Mention Everyone.

Before POSTing a test, the bot independently re-reads its permissions and checks that the channel and selected role are in the requested guild's currently eligible sets. It constructs the message itself using the shared validated template/identity contract. Interpolated metadata has `@` neutralized. Each request supplies `allowed_mentions` with `parse: []`, no users, no reply mention, and only the selected role ID (or an empty role list). A template cannot add another role or everyone ping. Embeds are suppressed with message flag 4. The message has a deterministic short nonce and `enforce_nonce: true`, which provides Discord's recent-window protection rather than a permanent exactly-once guarantee.

## API and authorization

All public operations independently require the database-backed Discord session, development allowlist and fresh owner/Administrator/Manage Guild permission for the URL's server. Channel/role/subscription IDs from the browser are never grants of access. Queries are guild-scoped, mutations use exact-Origin/CSRF checks and actual streamed JSON is limited to 12,000 bytes. Responses use no-store and sanitized errors.

Under `/api/guilds/:guildId/notifications`:

| Path                       | Method | Behavior                                                                                        |
| -------------------------- | ------ | ----------------------------------------------------------------------------------------------- |
| `/`                        | GET    | List current registrations and saved configuration.                                             |
| `/targets`                 | GET    | Retrieve eligible channels/roles through the bot broker.                                        |
| `/:subscriptionId`         | PUT    | Validate and save `{config, version}`; return the committed row.                                |
| `/:subscriptionId/preview` | POST   | Validate draft `{config}` and return labelled sample text; no write/send.                       |
| `/:subscriptionId/test`    | POST   | Use saved configuration and `{requestId, version}`; browser-supplied config/content is ignored. |
| `/:subscriptionId/disable` | POST   | Restrictive disable using `{version}` only, without changing destinations.                      |

The bot broker adds GET `/internal/guilds/:guildId/notification-targets` and POST `/internal/guilds/:guildId/test-notification`. It binds only to 127.0.0.1, authenticates with the existing shared secret using constant-time comparison before reading mutation bodies, limits incoming bytes and returns public IDs/names or safe status codes. The browser receives neither this secret nor the bot token. Web-to-bot calls refuse redirects and have 20-second read/30-second test deadlines. This is still a local single-host design; do not expose the broker publicly.

Discord checks are point-in-time; changes can race subsequent network calls. Bot-side revalidation minimizes the interval and Discord's POST response remains authoritative. An already initiated explicit test cannot be recalled by saving disabled settings afterward. Future automatic-send/disable serialization is not implemented or claimed here.

## Persistence, concurrency and lifecycle

Migration: `packages/database/migrations/0002_phase05_notifications.sql`, after the auth and registration migrations. Review it before `npm run db:migrate`. The referenced subscription `(guild_id,id)` unique index is deliberately created **before** the composite foreign key; the generated ordering was corrected and the final SQL is exercised in embedded PostgreSQL.

- `notification_settings`: subscription primary key, guild/channel/optional role IDs, template, enabled=false default, positive version and updated timestamp. A composite `(guild_id,subscription_id)` FK to the existing subscription prevents cross-guild associations. Removing/expiring a registration cascades its settings. Channel/role IDs reference external Discord state rather than pretending a local FK proves current permissions.
- `notification_test_attempts`: guild/request uniqueness, internal subscription ID, settings version, pending/sent/failed/uncertain status, safe error code and creation instant. It stores no rendered content, provider account ID, credentials or Discord message ID. This is bounded test admission/history, not a general notification delivery queue.

Optimistic versions prevent stale saves from overwriting another tab's edits. Test admission uses a short database transaction and registry lock, verifies the saved version, and permits at most one newly admitted test per server every **30 seconds**, including failed attempts. Replaying the same guild/request UUID and settings binding returns the recorded result without another send; conflicting bindings are rejected. The shared lock is held only during database admission, never over Discord HTTP. A test uses the accepted saved snapshot; later edits do not rewrite an in-flight request.

Successful Discord acknowledgment is recorded as sent; definite pre-send/rejection failures as failed; transport or ambiguous acknowledgment failures as uncertain. A pending record encountered after restart is treated as uncertain and is never automatically resumed. The browser does not retry sends automatically. A new explicit click creates a new request UUID; following an uncertain result, the UI instructs the operator to inspect Discord first because a new click can duplicate an already accepted message. Database completion failure also returns uncertainty. This is deliberately not a permanent exactly-once assertion.

Admission history expires after seven days, pruned on test admission and by the existing daily `npm run db:prune-streamers` command, now extended to prune test records as well. The existing 29-day provider metadata expiry and cascade behavior remain. There is no new scheduler: offline cleanup, backup expiry and deletion remain operator duties. Privacy/terms notices now disclose settings, explicit role-mentioning tests and bounded result history. No real database cleanup was executed during development.

## Local setup and actual acceptance

No new external dependency, OAuth scope, secret or Portal permission is required. The database package now declares its existing shared `@navi/core` workspace dependency. Keep bot credentials only in untracked `.env.bot`; web keeps the matching broker secret/URL in `.env.web`. Complete the existing auth configuration, start PostgreSQL, apply reviewed migrations, install the bot with the existing minimal permissions, and start web and bot services. In Discord, create ordinary text channels and make any desired non-managed alert role mentionable. Grant the bot View Channel/Send Messages through channel overwrites. Never enable Administrator as a workaround.

Manual acceptance once configured: select a test server, register both platforms, save different destinations, reload, preview, and explicitly send labelled tests. Check no unexpected mentions occur. Remove a channel/role/bot permission and verify safe failure; remove the bot and exercise restrictive disable. Revoke the user's manager role and verify direct API denial. Inspect an uncertain result before another test. Do not infer API or detection feasibility from a sample message.
