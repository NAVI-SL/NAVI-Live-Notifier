## Current topology and capacity boundary

Keep separate Next.js web, one Discord bot/Gateway+REST broker, one active monitoring leader and PostgreSQL. All monitoring/delivery state is durable SQL; Redis is not its queue. On the proposed single Linux host, apps share the TLS edge namespace to preserve private loopback broker binding. Keep 3000/4001/4100/5432 private; only approved edge ingress exposed. Replacing the edge container requires coordinated app recreation. No replica/autoscaling redesign is proposed.

The global unique provider/account identity supports shared monitoring. The historical synthetic ten-source/ten-guild case has 100 destinations; the current five-guild cohort at the ten-source ceiling has at most 50, with one destination per source subscription in a guild. Fan-out multiplies sends/permission reads even when polling is shared. The registry enforces its configured global source cap, while optional `BETA_GUILD_IDS` enforces at most five approved guilds in web and worker when configured. It is currently unset; `release:check` rejects that state for external release. No per-tenant source fairness quota or approved resource capacity is implied. Public installation still requires explicit approval and a privately reviewed target register.

Initial hardware sizing hypothesis from the deployment guide: Linux 2 vCPU/4 GB RAM/30–40 GB persistent SSD, build elsewhere if needed. No benchmark validates it. Web and worker each allow five query/two lock connections: **14 pooled application connections**, plus migration/admin/health headroom. Choose an operator-reviewed DB connection limit with at least that headroom; measure actual connections. Session advisory locks require direct/session-preserving connections, not transaction-pooling assumptions.

## API accounting and backpressure

At the current 7200/day worker YouTube allowance, nominal poll interval is:

`max(60 seconds, ceil(86400 seconds × YouTube sources × 4 / floor(budget × 0.8)))`

At the worst-case four calls/cycle, one YouTube source runs every 60s, five every 300s and ten every 600s, each near 5760 calls/day with 1440 units reserved for confirmations/hints/retries. A second videos batch is only requested when needed. These are conservative arithmetic estimates, not observed project consumption; web lookups/diagnostics/other clients may share project usage outside worker reservations. At ten sources, delay beyond the nominal ten-minute cadence can exceed the ten-minute freshness window. Short broadcasts/indexing delays can still miss detection. No guaranteed detection SLA or Premiere exclusion is established.

Kick checks each active shared source about every 60s, refreshes identity periodically and reconciles subscriptions when public callbacks are configured. App token is reused until expiry. Read actual response limits and enforce Retry-After; do not invent a fixed Kick quota. Webhooks are hints; official current LIVE confirmation is required before dispatch. [Kick event setup](https://raw.githubusercontent.com/KickEngineering/KickDevDocs/main/events/introduction.md).

Bot requests share one REST limiter; fresh pre-send verification reads guild/channels/roles/member plus message POST, so budget roughly **five bot REST requests per destination** before cache reuse, plus health/install requests. A 100-destination burst can approach 500 calls, not 100. The current loop claims at most 50 deliveries per tick, with 10s scheduler and nonoverlap; actual REST delays add time. Do not promise that a burst drains within a fixed few seconds. User OAuth guild reads/refresh have separate user-sensitive limits. Display caches never authorize writes.

Respect Discord's returned bucket/global limits and Retry-After rather than targeting its ceiling. The documented bot global ceiling is 50 requests/second and route limits apply independently; repeated invalid requests can also trigger restrictions. This is a platform ceiling, **not NAVI's safe throughput target**. [Official rate limits](https://docs.discord.com/developers/topics/rate-limits). Do not create traffic to hit it. Process-local caches/limits are suitable only within the reviewed small single-host model; cross-process/public distributed enforcement needs design before horizontal scaling.

## Database, retention and backups

Existing indexes cover auth user/expiry, provider stable-ID uniqueness/expiry, guild/source subscription uniqueness/source join, settings guild lookup, test request/cooldown, and delivery status/due scheduling plus session/guild/channel uniqueness. No speculative index/migration is added. `sources()` reads monitoring state and joins eligible routes every tick; profile `EXPLAIN (ANALYZE, BUFFERS)` on isolated representative data before increasing scale. Measure FK/cascade and retention queries; do not run destructive profiling against the live DB.

Required migrations through 0006, serialized explicit migrator and least-privilege grants are in deployment files. Verify actual journal/role ownership, runtime denial of auth access/DDL for worker and configured TLS for any external database. Same-host private PG transport is not proof of encrypted disk/backups. Table owners/superusers and web application tenancy need separate checks; no RLS is implemented.

Proposed starting recovery targets: daily protected backups (RPO 24h), restore within four hours; **unmeasured, not promised**. Select encrypted storage/retention and stable auth-key backup privately. Run a timed custom-format restore into a separate DB, compare settings/session/delivery counts/constraints, apply deletion exclusions and reconcile messages sent since backup before enabling monitoring. Never use `down --volumes`, clear delivery history or bulk-requeue uncertain jobs. Follow [deployment backup instructions](DEPLOYMENT_GUIDE.md) and [deletion process](DATA_DELETION_PROCESS.md). No scheduled encrypted/offsite backup or verified restore exists yet.

## Monitoring and incident response

Owner is the provisional operator; public support/on-call contact **[SUPPORT_CONTACT — TO BE CONFIRMED]**. Before unattended use configure a private alert path and verify receipt. Suggested triggers: two consecutive failed health probes; no worker tick for 120s; queue age >120s excluding known mandatory waits; any uncertain send/unexpected ping/unauthorized access; repeated provider auth/429; disk <20%; missed daily backup or restore drill; certificate expiry under 14 days. Thresholds are proposals, not implemented alerts. Bot REST health does not prove Gateway presence; public web health does not prove settings-schema readiness. Check lifecycle and full dependency health separately.

Keep structured safe service/source/delivery/attempt IDs, endpoint templates, HTTP status, retry delay and bucket fingerprints. Do not log tokens, cookies, raw callbacks/signatures/payloads or env/connection strings. Log rotation exists in Compose; private collection, retention and actual alerting remain unconfigured. Public logs must not expose guild/user data beyond operational need.

On unsafe mention, wrong destination, duplicate or uncertainty: pause the actual worker via its owner, preserve ledger, inspect the actual Discord channel and safe logs, contain access if needed. On provider failure respect cooldown; on webhook failure retain authenticity checks and use reconciliation. On DB trouble preserve volumes and restore only in isolation. For a credible secret compromise, contain first and have the owner authorize credential remediation; never print suspected secrets.

Rollback: record current immutable artifact/schema/backup and compatible previous artifact first; stop worker, retain SQL, restore compatible app version, validate web/one bot/settings/schema, reconcile uncertainty, then resume only after approved evidence. If edge namespace changes recreate apps together. An older DB backup can lose deduplication records: do not resume until post-backup receipts/deletions are reconciled. No known tested previous artifact or completed drill exists. [Full rollback plan](ROLLBACK_PLAN.md), [operations runbook](OPERATIONS_RUNBOOK.md).
