## Implemented functionality

The independent worker monitors **shared stable provider identities once**, selecting only unexpired sources with both an enabled server subscription and enabled notification settings. It polls due sources approximately every 60 seconds, refreshes identity/candidate metadata every 15 minutes, accepts authenticated webhook hints, and reconciles Kick subscriptions hourly when webhooks are configured. The web application need not be running. The existing bot process must run because it alone owns the Discord bot token and REST sender.

PostgreSQL stores source schedules, initialization/baseline time, bounded YouTube candidate lists, hashed session identities, verified webhook receipt hashes, provider budgets/cooldowns and delivery records. Migrations: `0003_phase06_monitoring.sql` and `0004_phase06_baseline.sql`. The worker uses a PostgreSQL-backed queue, not an additional Redis/BullMQ dependency. The existing Redis URL scaffold configuration remains compatible but Redis is not a queue authority in this implementation. This is an explicit personal-development implementation choice; future higher-throughput architecture remains separate.

On the first successful observation, the worker establishes a persistent baseline. Streams already started at/before that instant are suppressed, including videos discovered later. Each new confirmed session creates at most one delivery per session/guild/destination through a database unique index. Settings and subscription activation timestamps must predate the start, and a ten-minute freshness window prevents stale catch-up. YouTube session identity is the video ID; Kick identity is the canonical UTC start instant under the stable broadcaster ID. Simultaneous platforms remain separate sources/events.

Before sending, the worker re-reads enabled/current settings, version and source expiry, confirms that the same session is still LIVE through the official API, and uses the **existing bot notification service**. Confirmation is shared between destination fan-out requests during the delivery pass. The bot independently revalidates current channel permissions and role eligibility, then uses the shared bounded renderer, explicit mention allowlist and enforced nonce. Automatic messages use actual title/watch URL without the sample TEST label; explicit Phase 5 tests retain their old sample rendering. Per-subscription coordination serializes send initiation against settings saves, disable and registration removal. The lock holder checks that its coordination connection is still held before initiating the broker POST.

Pending deliveries survive worker restart. A sending record orphaned for two minutes becomes uncertain, not a blind retry. Definite 429 responses are rescheduled up to five admitted attempts; pre-send confirmation failures can retry with a persisted delay. Ambiguous POST/network/5xx outcomes become uncertain. Changing settings or disabling/removing a subscription suppresses obsolete queued work. Already initiated requests cannot be recalled, and recent-window Discord nonce behavior does not provide permanent exactly-once delivery.

Structured JSON logs include source checks/baselines/errors, subscription reconciliation errors, delivery IDs, attempts and safe status/error categories. They exclude credentials, callback URLs, raw webhook bodies and provider responses. The dashboard describes the enabled-worker prerequisite and does not pretend to know whether the worker is healthy.

## API integrations and limits

### YouTube

- Official Data API v3 `channels.list(part=snippet,contentDetails,id=stable channel ID)` resolves the uploads playlist and refreshes public identity. `playlistItems.list(part=contentDetails,maxResults=50)` supplies recent candidates every 15 minutes.
- `videos.list(part=snippet,liveStreamingDetails,status,id=...)` checks at most 50 candidates per call. A notification requires `liveBroadcastContent=live`, an actual start time, no actual end time and public privacy status. Upcoming, ordinary, ended and private videos do not create LIVE messages. Missing IDs remain unavailable candidates, not proof of offline. Up to 100 candidates rotate through checks per source.
- Google hub subscriptions use the documented channel Atom topic. The worker requests a secret and a one-day lease; verified challenge responses record the **actual granted lease** and renew at 80%. Atom events only add candidates and wake reconciliation. They never establish LIVE themselves.
- The worker defaults to **7,200 regular API calls per Pacific calendar day**, with a configurable maximum of 8,000. Reservations and cooldowns persist in PostgreSQL across adapter/process restarts. This leaves headroom relative to the documented default 10,000 regular units; registration/other users of the same project still consume quota separately. No search polling, undocumented endpoint, scraping, extra-project quota evasion or owner-only broadcast API is used.

**Coverage limitations:** YouTube documents feed notifications for uploads/title/description changes, not universal go-live transitions. Recent uploads are not guaranteed to reveal every current/upcoming broadcast. This implementation therefore detects **discovered candidates**, not every arbitrary channel stream within a guaranteed delay. Candidate bounds, quota exhaustion and local downtime can miss a short stream. Resource fields do not establish a reliable public API Premiere discriminator; Premiere exclusion is **not certified**. Controlled scheduled/unscheduled/long-scheduled/Premiere experiments remain a release gate. These limitations are disclosed rather than bypassed through scraping.

Official references: [push notifications](https://developers.google.com/youtube/data/guides/push_notifications), [channels](https://developers.google.com/youtube/v3/docs/channels/list), [playlist items](https://developers.google.com/youtube/v3/docs/playlistItems/list), [videos](https://developers.google.com/youtube/data/reference/rest/v3/videos/list), [quotas](https://developers.google.com/youtube/data/determine_quota_cost).

### Kick

- An app token comes from the official client-credentials endpoint. Tokens are server-only, cached with expiry and invalidated on 401. Credential errors and provider cooldowns fail safely; there is no delegated streamer login bypass.
- `GET /public/v1/channels?broadcaster_user_id=...` refreshes a registered stable identity. `GET /public/v1/users/livestreams?user_id=...` confirms active broadcasts. It uses the current documented `broadcaster_user.id`, `channel.slug`, title and start fields. Numeric IDs are parsed/serialized losslessly.
- `GET/POST /public/v1/events/subscriptions` inventories and restores `livestream.status.updated` version 1 subscriptions for active broadcasters. App-token POST supplies the numeric broadcaster ID and webhook method. The callback URL is configured in the Kick Developer application, not invented in the subscription body.
- The hosted public key is fetched from `GET /public/v1/public-key`, cached and refreshed at a bounded rate on verification failure. RSA PKCS#1 v1.5/SHA-256 verification covers message ID, timestamp and exact UTF-8 body separated by periods. The receiver enforces a five-minute freshness window, known event/version/subscription/broadcaster and durable replay receipt. Signed events are still hints; REST confirms actual current LIVE before notification creation/delivery. Periodic checks recover missed/rejected events.

Official references: [current OpenAPI](https://api.kick.com/swagger/doc.json), [app-token event setup](https://raw.githubusercontent.com/KickEngineering/KickDevDocs/main/events/introduction.md), [signature construction/rotation](https://raw.githubusercontent.com/KickEngineering/KickDevDocs/main/events/webhook-security.md), [event payloads](https://raw.githubusercontent.com/KickEngineering/KickDevDocs/main/events/event-types.md).

Inactive/deleted sources stop being polled and their hints are ignored. Automatic upstream unsubscribe garbage collection is not implemented: remove obsolete Kick subscriptions through the operator's app inventory and allow YouTube leases to expire when removing sources. Hourly inventory restores active Kick subscriptions; it does not delete unrelated app subscriptions. Disabling all routes prevents delivery immediately subject to already initiated requests and stops active-source polling. Stream payload metadata is cleared after 29 days, receipt hashes after seven days; source-bound hashed deduplication keys/outcomes persist until the shared source is deleted. Cleanup runs while the monitor runs; offline cleanup and backups remain operator duties.

## Required environment variables

Use the new ignored **`.env.worker`** based on `.env.worker.example`; do not overwrite existing populated files or put secrets in frontend variables.

| Variable                               | Use                                                                                                                                |

| `DATABASE_URL`, `REDIS_URL`            | Existing worker configuration; PostgreSQL and all reviewed migrations are required. Redis remains unused by this queue.            |
| `MONITORING_ENABLED`                   | Defaults to `false`. Set `true` only after schema/services/settings are ready.                                                     |

| `KICK_CLIENT_ID`, `KICK_CLIENT_SECRET` | Worker app-token credentials for Kick.                                                                                             |
| `MONITOR_PUBLIC_ORIGIN`                | Optional exact **HTTPS** origin for external callbacks; leave absent for reconciliation-only operation.                            |
| `MONITOR_WEBHOOK_SECRET`               | At least 32 random characters, required with a public origin; protects YouTube callbacks/HMAC. Never log it or callback MAC paths. |
| `MONITOR_PORT`                         | Private listener port, default `4100`, bound to `127.0.0.1`.                                                                       |
| `YOUTUBE_DAILY_BUDGET`                 | Default `7200`, bounded 1–8000 regular API requests/day for the worker.                                                            |

Worker environment selection now permits provider credentials and the private broker secret; it still excludes Discord bot/OAuth credentials and the web authentication secret. There is no automatic inheritance from `.env.web`. Missing provider credentials produce safe errors for that provider while other configured providers continue. Credential files were not created/populated or changed during implementation.

## Webhook configuration

1. Review/apply all migrations in the intended development database. Verify `npm run db:check`. Configure an enabled registered streamer and enabled destination using the existing authenticated dashboard.
2. Start the existing bot and configure the worker's matching broker credential. Set provider credentials privately. Run `npm run monitor:check`; use `npm run monitor:check -- --connectivity` for explicit **read-only** official API checks. That command never subscribes or sends.
3. For webhooks, put a TLS-terminating reverse proxy/tunnel in front of **loopback 4100**, forwarding only `/webhooks/*` and enforcing external HTTPS. Do not expose the bot broker, PostgreSQL or Redis. Set `MONITOR_PUBLIC_ORIGIN` to the exact HTTPS origin and provide the webhook secret. The worker does not trust forwarded headers as proof of HTTPS; TLS enforcement is the proxy/operator's responsibility.
4. In Kick Developer settings for the existing application, enable Webhooks and set **`https://YOUR-HOOK-ORIGIN/webhooks/kick`**. No new app, public Discord bot or privileged Gateway intent is needed.
5. Set `MONITORING_ENABLED=true` and start `npm run dev:worker` (or build, then `npm run start --workspace=@navi/worker`). YouTube topic/callback MAC and hub registration are generated internally per active source; do not manually paste or log credential-bearing callback URLs. Kick active-source subscriptions reconcile automatically.
6. YouTube verification GET accepts only a pending known channel/topic, matching callback MAC, subscribe mode and bounded challenge/lease. POST accepts only a valid hub HMAC and bounded Atom XML without DTD/entities. Unsigned distribution is rejected even if the hub omits a signature; official API reconciliation remains available. Kick POST uses hosted-key RSA validation and rejects stale/replayed/unrecognized events.
7. Look for safe `source_checked` baseline logs before starting a controlled **new** stream. Already-live onboarding is intentionally suppressed. Stop/restart the worker to exercise persisted state; stop the website separately to establish independence. Keep the bot/database running.

## Known limitations and remaining gates

- YouTube candidate discovery coverage and Premiere exclusion remain unproven. There is no universal go-live claim or guaranteed latency. Polling is bounded by per-source candidate caps, daily budget and offline runtime.
- Five-minute Kick signature freshness can reject a delayed valid retry; periodic official reconciliation recovers current streams within the ten-minute freshness policy. A stream missed while offline or already ended is not backfilled.
- Worker leadership/route coordination use dedicated PostgreSQL session locks and queued delivery claims; external multi-process/restart behavior still needs real infrastructure acceptance. Large deployments need measured fairness, batching and quota coordination, not untested scale claims.
- No automatic resend after uncertain outcomes, no permanent exactly-once guarantee, no event/delivery history UI, and no automatic upstream unsubscribe cleanup.
- Four existing moderate legacy Drizzle tooling-chain advisory findings remain as reviewed in the Phase 5 audit; no breaking downgrade was applied. Public release, retention/backup verification and complete device/accessibility validation remain separate gates.
