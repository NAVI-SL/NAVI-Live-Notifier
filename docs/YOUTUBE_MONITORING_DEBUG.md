# YouTube notification investigation and correction

Date: 2026-10-18 (Asia/Colombo). No credentials, dashboard preferences, application-row repairs, webhook subscriptions or deployment settings were changed manually. No real Discord send was initiated by the investigation. Platform reads and application-database inspection were read-only; regression delivery uses mocks. The existing worker can continue its normal state updates independently.

## Confirmed defect and incident evidence

The worker reconciled known YouTube video IDs roughly once per minute for one source, but discovered **new** IDs only every 15 minutes. With no public callback origin configured locally, there was no webhook to add a newly created broadcast between discovery runs. It could repeatedly check an older upcoming video while an entirely different broadcast started and finished unnoticed. Kick differs: its targeted status request directly returns current livestreams without this candidate-discovery dependency.

Evidence collected before changing application code:

- Effective worker configuration: monitoring enabled, YouTube key present, worker/web key equality true, no shell key override, no public callback origin, daily worker budget 7,200. Key values were never printed. Worker configuration precedence is shell environment, explicit `NAVI_ENV_FILE`, `.env.worker`, then `.env`; `.env.web` is not inherited.
- Actual official `channels.list`, `playlistItems.list` and `videos.list` requests all returned HTTP 200. The registered channel is `UC3kSms8BUqQG4SU9lJyQAaQ`, Navi Gaming, handle `@navigaming4625`; API identity matches it.
- Stored candidates contained only `U5IOr24FaQI`, which the actual API classified as public **upcoming**, with no actual start. Correctly, it did not produce a live event.
- A separate public broadcast, [`2vEizeon21g`](https://www.youtube.com/watch?v=2vEizeon21g), belongs to the same registered channel. It started at **04:33:15 UTC / 10:03:15 Colombo** and ended at **04:34:39 UTC / 10:04:39 Colombo**, lasting 84 seconds. It appeared in the current uploads response but was absent from stored candidates. The scheduled metadata rediscovery was 04:44:20 UTC, after its end.
- The source was initialized, with baseline 04:29:20 UTC, one enabled subscription and one enabled notification route. There were **zero YouTube monitor sessions and zero YouTube deliveries** of any state. There was one historical Kick `sent` delivery. An earlier YouTube send/failure/deduplication row did not block this broadcast.
- Worker-local quota reservation count was 11 for YouTube with an expired cooldown, far below 7,200. Three diagnostic API requests were separate from that counter. No API credential/quota error was observed. Cloud-project total consumption/remaining quota was not available; web registration and other API clients may share the project.

The 15-minute discovery gap is confirmed by code and reproduced in the new regression. The recent 84-second video's metadata is consistent with the reported failure, but the user has not yet supplied the exact failed watch URL/start time. Original historical worker stdout was not retained for replay, so exact historical polling times and uploads visibility while that broadcast was live are not proven. No claim of a real-time observed YouTube transition is made.

## Fix

`apps/worker/src/monitor.ts` now discovers YouTube candidates on every due reconciliation, even if the persisted metadata `discoverAfter` is in the future. Kick keeps its original discovery/status cadence. Existing candidate merge/hint-generation protection, current LIVE confirmation, PostgreSQL job queue, destination uniqueness, attempts, safe mentions, uncertainty handling and bot-owned REST sender remain unchanged.

The polling formula budgets **three one-unit calls per source per cycle** (`channels.list`, `playlistItems.list`, `videos.list`), with 20% of the configured budget reserved for confirmations/hints/retries:

`max(60 seconds, ceil(86,400 seconds × YouTube source count × 3 / floor(daily budget × 0.8)))`

At 7,200 units/day: one source polls every 60 seconds, ten sources nominally every 450 seconds. The process scheduler wakes every ten seconds and never overlaps ticks. Actual observation adds scheduler alignment, API/database latency and provider availability. Discovery no longer waits for the old 15-minute timestamp, including immediately after deploying this fix. Provider errors still reschedule safely and persistent admission prevents quota overrun; no polling/search bypass was added.

`apps/worker/src/providers.ts` adds projected `youtube_api` logs: endpoint name, HTTP status, local reserved unit count, categorized errors and retry delay. No full URLs, query parameters, response bodies or API keys are logged. Source logs include discovered candidate count, current live count, baseline flag and scheduled interval. Worker startup logs include only key-presence and budget/scheduler metadata, never the key.

The official API fields remain authoritative: a public video must have `liveBroadcastContent=live`, `actualStartTime` and no `actualEndTime`. Upcoming and completed broadcasts are not sent; the scheduled start time is not proof of LIVE. See [Google video fields](https://developers.google.com/youtube/data/reference/rest/v3/videos#liveStreamingDetails), [playlistItems.list](https://developers.google.com/youtube/data/reference/rest/v3/playlistItems/list), [videos.list](https://developers.google.com/youtube/data/reference/rest/v3/videos/list), and [push notifications](https://developers.google.com/youtube/data/guides/push_notifications). Push identifies new/updated videos; a hint still requires API confirmation. Uploads/search coverage and platform indexing delay remain provider limitations.

## Pipeline and deduplication review

Discovery → candidate merge → `videos.list` actual LIVE classification → transactional `repo.observe` → source/session hash and unique session/guild/channel delivery → pending → exclusive claim/sending → current settings/version/activation validation → second LIVE confirmation → existing bot broker → fresh channel/role/permission checks → Discord REST → attempt-fenced sent/pending/failed/uncertain result.

Upcoming or failed API observations do not insert sessions or consume a notification. A confirmed stream already live during onboarding, started before the route/baseline, or older than ten minutes is deliberately suppressed. Settings edits after stream start invalidate delivery under the existing activation policy. A confirmed `sent` record must not be deleted to force a repeat; `uncertain` records must not be blindly retried. This investigation did not reset any deduplication records or backfill ended streams.

3. Run `npm run build:shared`. In separate terminals run the existing `npm run dev:bot` and `npm run dev:worker`; stop an existing instance with Ctrl+C first instead of starting duplicate processes. Production-style invocation requires `npm run build` first. Keep the original service-specific secret files private. Local polling needs no public tunnel or callback change.

Check private local worker health using the existing `npm run beta:health` command; it probes without sending, although its overall result also depends on web availability. Require worker database/provider health and bot broker health OK before starting a broadcast. `npm run monitor:check -- --connectivity` checks credentials read-only but does not prove that a worker is running.
5. Wait for a successful `source_checked` for the registered source with `liveCount:0`. For a newly added source, let the first baseline complete. An upcoming candidate may exist; it must not trigger a message yet.
6. Start a **new public YouTube livestream** on that channel, preferably one with a newly created video ID to exercise discovery. Record its public watch URL and actual start time. In Studio actually start broadcasting; scheduling/preview mode alone is insufficient. Keep it live for at least five minutes for this one-source test. Do not edit notification settings midstream.
7. Observe projected worker logs: successful channels/playlistItems/videos calls, `youtube_discovered`, then `source_checked liveCount:1`, then `delivery_attempt state:sent`. Expect nominal detection on a subsequent 60-second cycle, plus up to a scheduler turn/API lag; this is not a guaranteed SLA. If the upstream API never exposes a live candidate before it ends, record that as an unresolved provider-discovery limitation.
8. In the approved Discord channel, manually verify exactly one notification with the saved message, channel name, current title, clickable correct watch URL, thumbnail and red embed. A broker `sent` response alone is not proof of visible client receipt. Record detection/send/receipt timestamps.
9. Leave it live through at least two further polls. Verify the persistent delivery remains sent and message count remains one. Restart only the worker while the same stream remains live and verify no duplicate. Close the browser to verify monitoring independence. End the stream and confirm no additional live alert.
10. If nothing arrives, retain only redacted event/status/error fields and the public video URL/time. Distinguish: candidate absent, API not actually LIVE, baseline/stale suppression, pending retry, failed permission/embed check, unavailable broker, or uncertain response. Do not delete session/delivery rows, disable LIVE checks, replay ended broadcasts or blindly retry uncertain sends.
