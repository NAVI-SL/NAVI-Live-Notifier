## Major findings and required fixes

### M01 — Known YouTube candidates can be starved indefinitely

**New confirmed implementation defect.** Locations: `packages/database/src/monitoring.ts:84`, `apps/worker/src/monitor.ts:94–109`, `apps/worker/src/providers.ts:299`.

Every due YouTube poll discovers the latest uploads and prepends them to retained candidates. `observe()` checks only `candidates.slice(0, 50)`. If discovery returns 50 recent IDs, a previously known/hinted scheduled broadcast outside that group is moved behind those 50 **on every poll**. Reconciliation retains the unchecked tail, but the next merge again prepends the same uploads. Retention therefore does not guarantee that a known candidate is ever observed. A valid webhook hint can suffer the same displacement before REST confirmation.

**Reproduction using current implementation:** migrate a fresh in-memory PGlite database through 0006; add one synthetic YouTube source and enabled route; establish an offline baseline; insert a known candidate through the real receipt repository. Simulate discovery returning 50 different recent ordinary videos. The videos fixture would report the known candidate as public/current LIVE, started after baseline, if requested. Advance three 60-second cycles through the real `createMonitor`, provider adapter and repository. All HTTP calls are fixtures; no application database or Discord endpoint is used.

```json
{
  "cycles": 3,
  "checkedPerCycle": [50, 50, 50],
  "knownCandidateRetained": true,
  "knownCandidateEverChecked": false,
  "sessionsCreated": 0,
  "deliveriesCreated": 0,
  "brokerSends": 0
}
```

The diagnostic exits 0 because it successfully asserts the defect; **the detection requirement fails**. The existing 335-test suite lacks this boundary. The repeated merge/slice ordering demonstrates indefinite starvation while discovery remains the same; three simulated cycles are not a real-world latency measurement.

**Required fix:** ensure all retained eligible candidates receive a bounded opportunity for official status verification, including hints/long-scheduled broadcasts outside the newest 50. Use a deliberate batching/rotation/prioritization policy and account for additional calls in the daily budget/cadence. Preserve generation-safe merges, stable ownership checks, LIVE confirmation, baseline/freshness and deduplication. Do not scrape or add undocumented endpoints.

**Closure:** regressions with exactly 50 and more than 50 known candidates, a hinted candidate outside the uploads window, repeated rediscovery and worker reconstruction must eventually check the candidate and admit one eligible alert per destination within the supported policy. Keep quotas and negative upcoming/ended cases correct. This audit does not implement the fix.

### M05 — YouTube coverage and latency still lack an accepted measured boundary

The previous 15-minute local discovery gap was fixed and its regression passes. That does not establish complete feed/uploads discovery, Premiere exclusion, API indexing delay or short/long-scheduled stream coverage, and does not resolve M01. Default nominal polling is 60 seconds for one YouTube source and 450 seconds for ten with budget 7200; actual latency includes scheduler/API delay. The 10-minute freshness window can suppress delayed starts. No quota-console/workload or observed latency matrix establishes release targets.

Google documents push notifications for uploads and title/description updates, not a universal go-live event. [Official push contract](https://developers.google.com/youtube/data/guides/push_notifications). The code's REST confirmation is necessary but cannot discover a video it never checks.

**Required evidence:** after M01 correction, measure scheduled/unscheduled/long-scheduled/short broadcasts, already-live onboarding, ordinary uploads and Premiere cases. Record misses as well as successful latencies and actual quota usage. Disclose and obtain owner acceptance of supported beta coverage; do not claim completeness or a latency guarantee from fixtures.

## Minor findings and residual risks

### N01 — Four moderate dependency findings remain

Fresh production-classified npm audit reports `drizzle-kit`, `@esbuild-kit/esm-loader`, `@esbuild-kit/core-utils` and nested `esbuild`, zero high/critical. These are affected packages in an existing tooling chain, not four independent root vulnerabilities. Npm proposes a semver-major change to Drizzle Kit 0.18.1; blindly applying it is not a safe fix. No exposed affected tooling server was demonstrated. Resolve through a tested compatible upstream change or record owner risk acceptance/exposure controls; scan the actual Linux image when available.

### N02 — Current contracts and evidence pointers need reconciliation

`04-database-schema.md` still leads with 0006 unapplied/unavailable wording despite the later workspace repair. `05-security-and-risks.md` leads with YouTube-only everyone/Kick unchanged wording despite the current both-platform dropdown. The beta/operations snapshots describe worker disabled/bot healthy; today's projected configuration is enabled/all probes unavailable. These dated observations must not be treated as today's state. Original historical audits should retain their original results; add clear current pointers/dates instead of rewriting evidence. Current audit evidence supersedes the old hash baseline for the selected audited inputs, not as a deployed release identifier.

### N03 — Private health and deployment hardening have limited scope

Bot health checks REST identity, not Gateway acknowledgement/visual presence. Public web health is liveness; its private container probe checks only `auth_user`, not the complete settings schema. `unless-stopped` restarts exited processes, not unhealthy ones. Single-owner Gateway protection is host-local and cannot prevent Windows/Docker-VM duplication. Base images remain floating/unscanned, strict script CSP is partial and actual file ACL/TLS/private ingress checks are pending. Keep these limitations explicit and enforce deployment/operational acceptance before unattended or public use; no exploit is demonstrated here.

### N04 — Earlier registration recovery/rate-limit edges remain in source

The Phase 4 findings remain visible in `apps/web/src/components/streamer-manager.tsx` and `apps/web/src/lib/streamer-providers.ts`: successful add/PATCH/DELETE is followed by a separate GET under the same error handler, so a failed refresh can leave success plus failure/stale controls. The provider lookup limiter clamps Retry-After to 86400 seconds, potentially retrying before a longer instructed delay. Its credential classifier still relies on HTTP 401/403, so HTTP 400 `invalid_client` can appear as generic outage. These are carried-forward source-reviewed defects, not newly induced external failures. The worker's durable longest-cooldown correction is separate and should not be mistaken for fixing the web lookup adapter. Add focused corrections/regressions without weakening authorization or retry timing.
