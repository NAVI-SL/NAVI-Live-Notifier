## Confirmed corrections

### 1. Patched the inherited transformer dependency

The old `@esbuild-kit/core-utils` loader resolved nested **esbuild 0.18.20**, causing the four package-level moderate findings through the Drizzle tooling chain. The vulnerability affects esbuild's serve behavior through 0.24.2; upstream patches begin at 0.25.0. [Maintainer advisory](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99).

Added the narrow root override `@esbuild-kit/core-utils → esbuild 0.28.2`, regenerated the stale nested lock resolution and performed a clean install. The existing root transformer was already 0.28.2; Drizzle's separate 0.25.12 branch stays unchanged. No unrelated existing dependency version, ORM, auth library or application schema was upgraded/downgraded. Drizzle Kit remains 0.31.11. No forced audit downgrade or dependency-source edit is retained.

Earlier override-only attempts kept the old nested resolution. This attempt explicitly invalidated that stale lock entry in an isolated trial before resolving and clean-installing. A zero audit result was not accepted alone: the actual loader's module resolution, executable CJS/ESM transforms, source maps, typed config loading, scratch migration generation/check and SQL execution are now covered by three new regressions. All pass on Windows and inside the Linux Docker build. The production-only image also resolves **0.28.2** and executes a transform successfully. Both current full and production audits return **exit 0, zero findings**. This is current dependency evidence, not a complete OS/image security certificate.

**Remaining npm caveat:** `npm ls esbuild --all --json` still returns **exit 1 / ELSPROBLEMS**, showing the original parent dependency range against the deliberately overridden version. The clean installed loader and lockfile resolve patched versions. This is consistent with the open npm 11 workspace-override [issue #9514](https://github.com/npm/cli/issues/9514), rather than evidence that the old executable remains installed. That attribution is an inference from matching behavior, not a claimed upstream fix. The listing warning is not hidden or counted as PASS.

Use **`npm ci` with the committed lockfile**, followed by `npm run check` and full/production audits. Do not blindly run `npm update`, `npm upgrade` or `audit fix --force`: npm's workspace override behavior can restore older dependencies. The new resolution/lock regression fails if an affected esbuild returns. The Dockerfile now runs `npm run test:tooling` before the application build, making this an image-build gate too. Recheck this caveat after any npm/dependency update; no package-manager migration was introduced.

### 2. Prevented upstream forwarded-host spoofing

A new actual Nginx/TLS fixture reproduced client-supplied `X-Forwarded-Host: spoofed.example` reaching the upstream unchanged, even with an accepted `Host`. This can confuse framework host/origin handling. No NAVI authorization bypass or data disclosure was demonstrated, and existing exact-Origin/guild guards remain unchanged.

Added `proxy_set_header X-Forwarded-Host $http_host;` beside the existing Host/protocol normalization. It preserves the accepted host and port while replacing the untrusted forwarded host. This changes the source configuration only. No deployed runtime, public domain, port publication, real certificate, redirect, permission or account allowlist was changed.

Added **`npm run test:proxy`**, an explicit optional Docker integration command. It starts uniquely named, network-disabled Nginx and synthetic HTTP upstream fixtures, exposes no host ports and uses a temporary self-signed localhost certificate explicitly trusted by its test client. It never starts the real website, bot or worker and never loads real environment files. Containers and synthetic certificates are removed on completion; cleanup refuses unexpected filesystem targets.

The before-fix run failed exactly the forwarded-host assertion. After the correction, **all 14 checks pass**: trusted local TLS, response security headers, canonical forwarded host, HTTPS protocol normalization, Forwarded removal, unknown Host rejection, safe HTTP rejection, private route blocking, YouTube/Kick callback routing, unknown callback rejection, request-body limit, auth burst throttling and OAuth query omission from logs. Callback routing uses synthetic upstreams; it is not real signature/provider callback acceptance.
