## Blockers and secure communication

**Major — split-host broker:** `BOT_INTERNAL_URL` only accepts `http://127.0.0.1:<port>`. Both the web and worker call authenticated `/internal/guilds/...` APIs; the worker also probes broker health. The bot binds `127.0.0.1:4001`. Separate services have separate loopback interfaces. A public broker URL is deliberately rejected. Render Free cannot receive private network traffic. No insecure workaround was added.

**Major — bot/worker Free runtime:** combining bot and worker on one machine preserves their loopback communication, but does not connect the separate dashboard. Existing entrypoints also lack `0.0.0.0:$PORT` ingress or a combined supervisor. A proper combined service would require lifecycle ownership, signal propagation, meaningful health aggregation and verified hook routing. Those changes alone would not solve sleeping, quotas or cross-host access, so no placeholder combined command/health endpoint was introduced.

**Major — continuous monitoring:** Render Free sleeps after 15 minutes without inbound traffic, wakes in about one minute, uses ephemeral filesystems and offers 750 shared instance-hours/month. Other service types lack Free instances; services may restart or be suspended for usage limits. Two continuously running instances need 1,440 hours in a 30-day month. Outbound Gateway/polling traffic must not be assumed to keep a service awake. No keepalive traffic is configured. These limits make continuous notification guarantees unavailable. [Render Free documentation](https://render.com/docs/free).

**Major — edge parity:** native dashboard hosting bypasses current Nginx API throttling/host and path controls. Next security headers and Better Auth protections remain, but are not equivalent to the complete edge configuration. Public experiments need an explicit bounded access/security review; a green liveness check is insufficient.

Safe direction for review: keep all three processes behind the existing edge on one approved always-on Linux host, or separately approve a secure cross-host broker architecture with paid/private networking as applicable. No host selection, purchase or architecture redesign was performed.

## Neon compatibility and persistence

Use native `pg` TCP with a **direct** connection string and `sslmode=verify-full`. Current driver parsing retains certificate/hostname verification; regression coverage constructs a synthetic client without connecting. Never use `sslmode=no-verify`, `NODE_TLS_REJECT_UNAUTHORIZED=0` or disable certificate verification to resolve errors. [Neon secure connection guidance](https://neon.com/docs/connect/connect-securely).

Neon's pooler is transaction-mode PgBouncer and does not support session advisory locks. NAVI uses those locks for OAuth refresh and notification coordination; therefore a `-pooler` hostname is unsuitable for the current `DATABASE_URL`. Direct connections are also appropriate for migrations and backup tools. Account connection limits must cover all query/lock pools and overlap during restarts. [Neon pooling documentation](https://neon.com/docs/connect/connection-pooling).

Exact migration steps are in the Render README. Use a separate privileged migration session, then least-privilege runtime roles. Migration safety, TLS handshake, role grants, cold-compute latency, concurrent locks and restoration against **actual Neon** remain BLOCKED without an approved test database. Current 5-second connect/1-second lock-query budgets must be measured against cold compute before tuning. No timeout change is justified by a hypothetical failure.

Continuous 10-second scheduler activity can keep compute active. Neon Free currently documents 100 CU-hours/project/month, 0.5 GB storage, 5 GB network transfer and scale-to-zero after inactivity; verify the actual account entitlement before deployment. No capacity/uptime guarantee follows from the local tests. [Official Neon Free quota FAQ](https://github.com/neondatabase/website/blob/main/content/faqs/free-plan-limits-and-quotas.md).

## Upstash compatibility

Use the console's native Redis hostname/port/password through `rediss://`; percent-encode credentials and retain certificate validation. Do not substitute the REST URL or REST token into the TCP URI. TLS is documented as enabled by Upstash. [Connection instructions](https://upstash.com/docs/redis/overall/getstarted), [security](https://upstash.com/docs/redis/features/security).

Upstash documents native Redis TCP, Pub/Sub and queue use cases. Its REST API also supports Pub/Sub, but that does not make ephemeral Pub/Sub a durable delivery ledger. NAVI has no BullMQ/Redis queue or Pub/Sub dependency; moving jobs there would be unrelated redesign. BullMQ compatibility is provider-documented, with polling command-cost caveats, not a tested NAVI integration. [Use cases](https://upstash.com/docs/redis/overall/usecases), [REST API](https://upstash.com/docs/redis/features/restapi), [BullMQ](https://upstash.com/docs/redis/integrations/bullmq).

Actual TCP/TLS PING, bounded publish/subscribe and queue-command tests against Upstash remain BLOCKED until an approved endpoint exists. Such probes must use isolated disposable keys/channels and no application jobs. Free pricing currently lists 250 MB, 10 GB monthly bandwidth and 500K monthly commands; avoid idle queue polling or auto-upgrade. Recheck entitlements in the owner's console. [Upstash pricing](https://upstash.com/pricing/redis).

## HTTPS, OAuth and webhook requirements

Render web ingress requires `0.0.0.0` and its assigned `PORT`; managed HTTPS is available. The example uses the existing Next health route and forwards signals directly via shell `exec`. No worker or broker is attached. [Render web services](https://render.com/docs/web-services), [Blueprint fields](https://render.com/docs/blueprint-spec).

The existing Better Auth callback is `${WEB_ORIGIN}/api/auth/callback/discord`. Configure exactly the approved HTTPS origin and callback in Discord; keep `identify guilds`, secure sessions, state validation, user/guild allowlists and private bot installation. There is no separate invented `DISCORD_REDIRECT_URI` environment variable. No Portal setting was inspected/changed for this task. [Discord OAuth2](https://docs.discord.com/developers/topics/oauth2).

Kick requires its application webhook setting to target the approved reachable `/webhooks/kick` endpoint. Preserve raw-body verification using message ID, timestamp and RSA signature with the hosted public key; the implementation also checks event/version/subscription identity. Request only the existing status event. Repeated failures can remove subscriptions, so a sleeping endpoint is a delivery risk. No external subscription was created/renewed. [Kick events](https://github.com/KickEngineering/KickDevDocs/blob/main/events/introduction.md), [webhook security](https://github.com/KickEngineering/KickDevDocs/blob/main/events/webhook-security.md).

YouTube callbacks remain the generated per-channel HMAC paths; challenge verification and authenticated hints must still be followed by official live-status verification. Feed updates are hints, not proof of LIVE. [YouTube push notifications](https://developers.google.com/youtube/v3/guides/push_notifications).

## Shutdown, restart safety and operations

Existing bot shutdown stops Gateway, broker and local lease, with a 10-second watchdog. Worker shutdown aborts outbound requests, stops scheduler/server and closes database pools, with a 30-second watchdog. Discord.js handles reconnects; PostgreSQL reconnect/error handling and persistent claim/uncertain recovery remain intact. Tests exercise these with synthetic services. Sudden platform termination cannot guarantee delivery; preserve `uncertain` outcomes and never blindly retry them.

Store auth/settings/deliveries only in PostgreSQL; do not rely on the Render filesystem for backups, logs or lock durability. Keep auth/webhook secrets stable and single bot owner during deployment overlap. Bot/worker health is private readiness; website health is public liveness only. No fake health wrapper was added. External alerts, sustained availability, offsite restore and hosting resource/cost measurements remain acceptance gates from Phase 14D.
